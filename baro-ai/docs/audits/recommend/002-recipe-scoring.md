# Recommend Architecture Audit 002 — 레시피 후보 스코어링 로직 (2026-09-04)

사용자가 채팅에서 제기한 문제의식("스코어링 로직이 쓸데없이 복잡하고, 얼마나 도움이 되는지 체감이 안 됨")을 코드·스펙 문서로 직접 검증한 결과다. 반드시 고칠 A 항목, 유지보수성 B 항목, 유지가 더 나은 D 항목 모두 **0건**이고, 참고 사항 C 항목이 **1건**이다. **코드 변경 없이 기록만 남긴다** — 사용자가 나중에 시간이 날 때 직접 검토 후 수정을 지시할 예정이라, 이번 라운드는 승인·구현 단계를 진행하지 않는다.

## 범위

- 대상 코드: `com.barofarm.ai.recommend.domain.RecipeCandidates.chooseBest()`, `CandidateRecipePlan.calculateScore()`
- 감사자: 사용자가 채팅에서 제기한 문제의식을 이 세션에서 직접 코드로 확인했다. `safe-refactor`가 정한 "신선한 서브에이전트 감사"가 아니라 채팅 검증으로 대체한 점을 명시한다 — 이 코드는 이번 세션에서 새로 작성한 게 아니고, 사용자가 이미 비판적 검토를 명시적으로 요청한 상태라 self-grading 편향 우려가 낮다고 판단했다
- 기준: `baro-ai-performance-refactor.md` 근거 기준, `core-guardrails.md` ⛔ STOP §1(문서·구현 정합)
- 관련: [`recommend/001-llm-prompt-tuning.md`](001-llm-prompt-tuning.md)(같은 도메인 앞 라운드, 프롬프트 내용만 다뤘고 이 스코어링 로직은 범위 밖으로 명시했었다)

**STOP §1(문서·구현 정합) 확인**: [`docs/specs/cart-recipe/recipe-recommendation.md`](../../specs/cart-recipe/recipe-recommendation.md)(2026-09-04 감사 당시 경로는 `specs/recommend/`)의 `## 비즈니스 규칙` 표(47-55줄)에 이 스코어링 가중치·정책이 빠져 있다. 24번째 줄에 "레시피 후보 생성 및 최적 후보 선택(`RecipeCandidates.chooseBest`)"이라는 완료 체크박스만 있고, "최적"의 정의(가중치·판매 기회 보너스)는 스펙 어디에도 없다. 스펙 헤더도 `> 관련 BR: N/A`(5줄)로 별도 BR(Business Rule) 문서가 없음을 명시한다 — 즉 이 계산식이 사실상 이 정책의 유일한 표현이고, 문서로 검증된 적이 없다.

## ✅ A. 반드시 수정해야 하는 사항

**없음.** 코드로 확인 가능한 버그·성능 저하를 찾지 못했다 — 아래 C-1은 "설계가 불투명하다"는 문제이지 "동작이 틀렸다"는 근거는 아니라서 A로 올리지 않았다.

## ✅ B. 유지보수성 향상을 위한 리팩토링

**없음.** 아래 C-1이 다루는 스코어링 로직은 비즈니스 로직(사업 목표를 반영한 점수 정책)이라, 순수 유지보수성 개선(중복 제거·Dead Code 등)으로 다룰 항목이 아니다.

## 💡 C. 참고 사항 (권장하지만 이번엔 수정하지 않음)

### C-1. 스코어링 가중치 미문서화·프롬프트 정책과 중복 가능성

`CandidateRecipePlan.calculateScore()`(27-62줄)는 다음 공식으로 점수를 매긴다.

```
점수 = 보유 핵심재료수 × 10 + 보유 추가재료수 × 3 + missingBonus
missingBonus: 부족 재료 0개면 -10, 1~2개면 +15, 3개 이상이면 -5
```

이 가중치(10, 3, -10, 15, -5)를 설명하는 문서·주석·A/B 테스트 근거를 `docs/` 전체에서 찾지 못했다(`grep -rln "calculateScore\|missingBonus\|판매 기회" baro-ai/docs/` — 이 문서를 쓰기 전 기준으로 0건). 값의 출처를 알 수 없어 "왜 10인지, 왜 15인지"를 지금은 아무도 설명할 수 없는 상태다.

더 근본적인 문제는 `missingBonus`가 보상하려는 정책("부족 재료 1~2개면 판매 기회 있음")이 `RecipeCandidateGenerator.java`의 프롬프트에 **이미 별도로 강제돼 있다는 점**이다 — "`recipeIngredientsCore` 재료의 30-50% 정도는 '보유 재료'에 없는 새로운 재료로 구성하여, 사용자에게 추가 구매를 자연스럽게 유도하세요"(81-83줄 근처). `recipeIngredientsCore`는 3~5개로 지정돼 있으므로 30-50%는 정확히 1~2개, `missingBonus`가 가점을 주는 구간과 겹친다. LLM(Large Language Model, 거대 언어 모델)이 프롬프트 지시를 잘 따른다면 애초에 후보 3개가 이 값에서 큰 차이가 안 나서, 서버 스코어링이 사실상 변별력이 없을 가능성이 있다.

정황 증거도 있다 — `RecipeCandidates.chooseBest()`(32-58줄)는 점수·난이도로 비교한 뒤에도 `Collections.shuffle`로 동점자를 랜덤 처리하는 코드를 별도로 두고 있다(51줄). 동점 처리 로직을 따로 만들어뒀다는 것 자체가 실제로 동점이 흔하다는 신호이고, 후보가 3개뿐인데 동점이 흔하다면 이 스코어링의 실질적 변별력이 낮다는 사용자의 체감과 맞아떨어진다.

로깅도 최종 선택 결과만 남긴다(`RecipeRecommendService.java:99` "최종 선택된 레시피: ..."). 선택되지 않은 나머지 2개 후보의 점수는 어디에도 기록되지 않아, 이 로직이 실제로 무엇을 걸러내고 있는지 지금은 관측할 방법이 없다.

**바로 삭제를 권하지는 않는다.** "LLM이 후보 여러 개를 만들고, 결정론적 규칙이 그중 사업적으로 유리한 것을 재선정한다"는 패턴 자체는 이 저장소가 이미 다른 곳(`enhanceWithServerValidation` — LLM 자기보고 값을 안 믿고 서버가 재계산)에서 택한 철학과 일치한다. 판매 유도처럼 사업적으로 민감한 결정을 LLM의 자체 판단에 맡기지 않고 감사 가능·튜닝 가능한 서버 로직으로 두는 것 자체는 정당하다 — 문제는 패턴이 아니라 **구현이 불투명하다는 것**이다.

**왜 지금 안 하는지**: 사용자가 시간이 날 때 직접 검토한 뒤 수정을 지시할 예정이다(2026-09-04 사용자 결정). 또한 이 로직은 순수 리팩터 대상이 아니라 **비즈니스 로직(사업 목표 반영 점수)**이라, `safe-refactor` 절대 원칙(비즈니스 로직·정책 변경 금지)에 따라 손대려면 "이 정책이 여전히 유효한가"부터 확인이 필요하다 — 아래 판단이 서지 않는 항목 참고.

## 🚫 D. 수정하지 않는 것이 더 좋은 사항

**없음.** "지금 구조를 그대로 유지하는 게 낫다"고 확정할 근거도 아직 없다 — C-1이 지적한 문제(가중치 미문서화·정책 중복 가능성)는 실재하고, 다만 그걸 지울지 로깅만 보강할지는 아래 "판단이 서지 않는 항목" 1·2번이 풀려야 정할 수 있어 D로 확정하지 않았다.

## 판단이 서지 않는 항목

1. **프롬프트의 "30-50%" 지시와 서버의 `missingBonus`가 의도된 이중 안전장치인지, 우연한 중복인지** — 둘 다 같은 정책(부족 재료 1~2개 선호)을 다른 계층에서 강제하고 있다. 하나로 합칠지, 의도된 defense-in-depth로 남길지는 설계 판단이 필요하다.
2. **"판매 기회 유도"(부족 재료가 있는 레시피를 우대)가 지금도 유효한 사업 목표인지** — 코드에 정책으로 박혀 있지만 이 결정을 내린 사업적 근거(전환율 데이터 등)를 문서에서 찾지 못했다. 여전히 유효하다면 스펙의 `## 비즈니스 규칙` 표에 이 정책과 가중치를 옮겨 적는 게 맞다.
3. **스코어링이 실제로 얼마나 변별력이 있는지** — 후보별 점수를 로그에 남긴 적이 없어 동점 발생 빈도·점수 분포를 실측하지 못했다. 로깅을 추가하는 것 자체는 위험도가 낮은 관측 개선이라, 정책 판단(1·2번) 전에 먼저 해도 되는 선행 작업일 수 있다.

## 승인 대기

A/B 항목 없음. C-1만 있고, 사용자가 나중에 시간이 날 때 직접 검토·지시할 예정이라 이번 라운드는 여기서 종료한다. 재개할 때는 위 "판단이 서지 않는 항목" 1·2번(정책 유효성 확인)부터 시작하는 것을 제안한다.
