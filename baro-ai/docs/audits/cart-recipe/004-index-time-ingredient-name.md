# Cart-recipe 측정 004 — 색인 시점 재료명 추출 프롬프트 (2026-09-06)

김치·두부·장류를 팔기로 정하면서([`스펙 갈래 B`](../../specs/cart-recipe/pantry-staples-and-catalog-coverage.md)), 상품명에서 재료명을 뽑는 프롬프트가 새 상품에서 제대로 동작하는지 확인한 기록이다. **걱정했던 것 대부분은 빗나갔고(16/17 통과), 딱 한 종류가 실제로 틀렸다.** 그 하나를 고쳐 17/17로 만들었고, 기존 농산물 6건의 답은 한 글자도 바뀌지 않았다.

이 값이 왜 중요한지부터 짚는다. `ProductDocument.ingredientName`은 **"장바구니에 무엇이 들었나"의 유일한 근거**다. 여기가 틀리면 그 뒤의 레시피 품질을 아무리 올려도 소용이 없다 — 김치를 담은 사람이 배추를 가진 것으로 읽히면 추천 자체가 딴 얘기가 된다.

## 어떻게 쟀나

측정 조건이다. 같은 값으로 다시 돌리면 재현된다.

| 항목 | 값 |
|------|-----|
| 실행 도구 | [`check_normalizer.py`](../../../scripts/goldenset/check_normalizer.py) — 앱·ES 없이 프롬프트만 Gemini에 직접 호출 |
| 입력 | 상품명 17종 (기존 농산물 6 · 김치류 4 · 두부·콩가공 3 · 장류 4) × 1회 |
| 모델 | `gemini-3.5-flash-lite`, **temperature 0.0** — 운영과 같다(추출이지 창작이 아니라서 0을 쓴다) |
| 판정 | 상품마다 "이 이름으로 색인되면 레시피가 성립하는가"를 허용 목록으로 미리 정해 두고 기계 비교 |
| 원본 | 아래 4개 |

**원본 파일 이름에 주의.** `current` 팔은 프롬프트를 Java에서 읽으므로, 파일 이름의 `current`는 "그 시점의 운영 프롬프트"라는 뜻이지 특정 프롬프트를 가리키지 않는다. 어느 게 무엇인지는 이렇다.

| 파일 | 무엇을 잰 것 | 결과 |
|------|--------------|------|
| `raw-normalizer-current-20260906-111719.jsonl` | **개선 전** 프롬프트(당시 운영) | 16/17 |
| `raw-normalizer-revised-20260906-111900.jsonl` | 개선안 1차 — 느슨한 판정 기준으로 17/17 | 회귀 있음 |
| `raw-normalizer-revised-20260906-112103.jsonl` | 개선안 2차 — 기준을 조인 뒤 | 17/17 |
| `raw-normalizer-current-20260906-112343.jsonl` | **개선 후** 프롬프트(Java 반영본) | 17/17 |


**개선 전 프롬프트를 얼려 뒀다.** [`normalizer_prompts.py`](../../../scripts/goldenset/normalizer_prompts.py)의 `pre-catalog` 팔이다. `current` 팔은 옮겨 적지 않고 **Java 파일에서 직접 읽는다** — 옮겨 적으면 언젠가 어긋나고, 어긋난 프롬프트로 잰 수치는 운영에 대해 아무것도 말해 주지 않는다.

**허용 목록은 필자 판단이다.** 예를 들어 "포기김치"는 불합격으로 뒀는데, 레시피가 "김치"라고 쓰지 "포기김치"라고 쓰지 않기 때문이다. 반대로 "열무김치"는 합격이다 — 열무국수·열무비빔밥은 일반 김치로 대체되지 않는다.

## 무엇을 알게 됐나

### 1. 걱정했던 것은 대부분 일어나지 않았다

프롬프트 문장만 읽고 위험하다고 본 것은 두 가지였다. **둘 다 실제로는 거의 일어나지 않았다.**

| 걱정한 것 | 실제 |
|-----------|------|
| "카테고리를 그대로 쓰지 말라"는 규칙 때문에 김치를 "배추"라고 답할 것이다 | 포기김치 → "김치", 묵은지 → "묵은지", 백김치 → "백김치". **안 그런다** |
| "수식어를 다 떼라"는 규칙 때문에 된장을 "콩"이라고 답할 것이다 | 된장 → "된장", 고추장 → "고추장", 순두부 → "순두부". **안 그런다** |

프롬프트를 읽고 추론한 위험과 실제로 일어나는 일은 다르다. [`003`](003-pantry-staples-and-variants.md)에서 S15 원인 추측을 기각했을 때와 같은 교훈이다.

### 2. 딱 한 종류가 틀렸고, 그게 가장 위험한 종류다

**열무김치 → "열무"** (17건 중 유일한 불합격)

열무김치를 담은 사람이 **열무(채소)를 가진 것으로 색인된다.** 그러면 두 가지가 한꺼번에 어긋난다. 열무김치가 필요한 요리에는 "김치를 사세요"가 뜨고, 열무가 필요한 요리에는 "이미 있다"고 판단한다.

**왜 이것만 걸렸나.** 원재료 이름이 상품명 안에 글자로 들어 있을 때만 그쪽으로 답한다. "포기김치"에는 "배추"가 없어서 안 걸렸고, "열무김치"에는 "열무"가 있어서 걸렸다. 그러니 이건 김치만의 문제가 아니라 **"○○김치"·"○○장" 꼴 상품 전반의 문제**다.

### 3. 고친 결과

규칙 두 줄과 예시 네 줄을 더했다. 기존 문장은 건드리지 않았다.

| | 개선 전 | 개선 후 |
|---|---------|---------|
| 전체 | 16/17 | **17/17** |
| 기존 농산물 6건 | 6/6 | 6/6 — **답이 한 글자도 안 바뀜** |
| 열무김치 | "열무" | **"열무김치"** |
| 포기김치 | "김치" | "김치" (유지) |

더한 규칙은 두 가지다.

1. **완성품은 완성품 이름으로.** "이미 만들어진 식품은 그 완성품 이름이 답입니다. 원재료로 되돌리지 마세요."
2. **레시피에 적히는 이름으로.** 담는 모양(포기·맛)은 빼고, 요리에서 바꿔 쓸 수 없는 종류(열무·순·유)는 남긴다.

두 번째 규칙은 한 번 실패하고 고쳤다. 처음엔 "종류를 가리키는 말은 남기라"고만 썼더니 **포기김치가 "포기김치"로 나왔다.** 담는 모양까지 남겨 버린 것이다. 그대로 뒀으면 김치를 가진 사람에게 김치를 사라고 하는 새 결함이 생길 뻔했다 — 재료 비교가 글자 완전일치라서다.

> 처음 허용 목록이 "포기김치"도 합격으로 뒀던 탓에 이 회귀가 O로 지나갈 뻔했다. **판정 기준이 느슨하면 측정이 회귀를 덮는다.**

## 남은 것 · 알려진 제약

| 항목 | 내용 |
|------|------|
| **17건이 전부다** | 상품명은 무한히 다양하다. 이 측정은 "새 카테고리에서 대놓고 깨지지는 않는다"까지만 말한다 |
| **조선간장 → "조선간장"** | 합격으로 뒀지만, 레시피가 "간장"이라고 쓰면 완전일치에 걸리지 않는다. 간장은 기본 양념이라 부족 재료로 잘 안 나와서 지금은 문제가 없다 |
| **완전일치 비교가 근본 제약이다** | 색인 이름과 레시피 이름이 한 글자만 달라도 어긋난다. [`003`](003-pantry-staples-and-variants.md)에서 동의어 사전을 만들지 않기로 했는데, 그 판단은 **색인 이름이 레시피 이름과 같게 나온다는 전제** 위에 있다. 이 프롬프트가 그 전제를 지키는 장치다 |
| **실제 상품으로는 확인 못 했다** | 카테고리도 상품 시드도 아직 없다. 여기 쓴 상품명 17개는 실제 판매 상품이 아니라 필자가 만든 것이다 |
