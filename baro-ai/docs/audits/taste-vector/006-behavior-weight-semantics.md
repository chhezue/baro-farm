# Taste-vector Architecture Audit 006 — 행동 가중치의 의미와 실제 동작 (2026-09-15)

행동 가중치(주문 3 · 담기 2 · 수량 변경 1 · 삭제·취소 0)가 스펙이 말하는 의도대로 작동하는지, 발행 모듈부터 취향 벡터 계산까지 따라가 확인한 감사다. 결과는 A 1 · B 4 · C 3 · D 3이다. 핵심은 A-1이다. 비중 0은 삭제 로그 한 줄만 버리고 같은 상품의 담기 로그를 지우지 않아서, "삭제는 관심 철회"라는 승인된 결정이 흔한 경우에 지켜지지 않았다. **A-1·B-1~B-4는 2026-09-15에 승인·반영했다**(아래 "승인 결과", 반영 기록은 [`refactor-log.md`](refactor-log.md)). 아래 A/B 본문의 "현재 동작"은 반영 전 코드 기준이다.

## 범위

- 대상 코드: `embedding.application.UserProfileEmbeddingService`, `embedding.domain.TasteProfile`, `event.consumer.*`, `log.*`, `recommend.application.PersonalizedRecommendService`·`VectorRecommendPipeline`
- 발행 측(읽기만 함): `baro-common` `HistoryEventType`·`@TrackHistory`, `baro-shopping` `CartService`·`Cart`, `baro-order` `InventoryConfirmedConsumer`·`InventoryCanceledConsumer`
- 감사자: 서브에이전트(읽기 전용, 결론을 주지 않고 "가중치 체계가 의도대로 작동하는가"만 질문) + 메인 세션. 서브에이전트 지적은 메인 세션이 git·코드로 다시 확인했고, A-1·C-1은 임시 단위 테스트로 재현했다(아래 "재현 기록")
- 기준: `audit-checklist.md`, `core-guardrails.md` ⛔ STOP, `baro-ai-performance-refactor.md` 근거 기준
- 계기: 가중치 값에 근거가 있느냐는 사용자 질문. `full-module/002`가 이 값을 "직관"으로 분류해 두었다

## 먼저 알아 둘 것 — 가중치가 결과에 작동하는 방식

- 가중치는 **상품이 아니라 로그 한 줄마다** 붙는다(`UserProfileEmbeddingService.java:107-110`).
- 비중 0인 로그만 걸러지고(`:141` `isUsable`), 남은 로그의 상품 벡터가 **로그마다 누적 합산**된다(`:191-206`).
- 경험 상품(개인화 추천에서 제외하는 상품, `experiencedProductIds`)은 걸러진 로그들의 상품 ID로 만든다(`:118`, `:132`).
- 결과 벡터를 길이 1로 맞추므로 절대값은 소거되고 **비율만 결과에 작동한다**(`UserProfileEmbeddingServiceTest.blend_uniformScalingCancelsOut`).

## ✅ A. 반드시 수정해야 하는 사항

### A-1. 삭제(비중 0)가 관심 철회로 작동하지 않는다

- **Priority**: High
- **Category**: Architecture (모델 정확성)
- **문제**: 상품을 담았다가 빼면, 삭제 로그만 버려지고 담기 로그(비중 2)는 남는다. 그래서 뺀 상품이 취향 벡터를 계속 끌어당기고, 동시에 경험 상품에도 남아 다시 추천되지 않는다. 사용자에게는 "뺀 상품과 비슷한 것만 계속 나오고, 뺀 상품 자체는 다시 안 나오는" 결과가 된다.
- **근거**:
  - 코드: 로그 단위 판정(`:107-110`), 로그 단위 누적(`:191-206`), 걸러진 로그로 만든 경험 상품(`:118`). 같은 상품의 "현재 상태"를 판정하는 단계가 없다.
  - 흔한 경우인지: 로그인 사용자가 상품 ID가 있는 삭제 이벤트를 만들려면 그 상품이 장바구니에 있어야 하고, 담을 때 `CART_ITEM_ADDED`가 발행된다(`baro-shopping/.../CartService.java:57`, `:111`). 삭제 로그만 있는 상품은 담기 로그가 30일·10건 창 밖으로 밀려난 경우뿐이다.
  - 재현: 임시 테스트 R1에서 `[삭제 P, 담기 P, 담기 Q, 주문 R]`로 계산하면 P가 경험 상품에 남고 벡터 성분이 `2/√17 = 0.485`다(아래 "재현 기록").
- **어긋나는 결정·문서**: `taste-vector/001` 판단 1(`001:299`, "가중치 0인 행동의 상품은 경험 상품에서도 뺀다 … 다시 추천해도 된다")이 실제로는 지켜지지 않는다. 같은 내용을 사실처럼 적은 문서는 B-4에 모았다.
- **왜 문제인가**: 승인된 정책과 코드 동작이 반대다. 테스트가 로그 → 프로필 경로를 다루지 않아(B-3) 지금까지 드러나지 않았다.
- **개선 방법** — 정책 선택이 필요하다(아래 "판단이 서지 않는 항목" 1번):
  - **(가) 코드를 정책에 맞춘다.** 비중을 매기기 전에 상품 단위로 상태를 정한다. 삭제는 **같은 상품의 그 이전 장바구니 로그(담기·수량 변경)만** 무효로 하고, 주문 확정은 건드리지 않는다. 주문 흐름은 장바구니를 비우지 않으므로(`removeItem` 호출은 컨트롤러뿐), 구매 뒤 사용자가 장바구니를 정리하면 삭제 이벤트가 들어온다. 이때 구매 신호까지 지워지면 안 된다.
  - **(나) 정책을 코드에 맞춘다.** 코드는 두고 "삭제 로그 자신만 빠진다"로 결정·문서를 고친다.
  - 음수 비중은 쓰지 않는다(D-2).
- **검증 방법**: 두 저장소는 인터페이스라 Mockito로 대체해 `computeProfile`을 부른다. `[삭제 X, 담기 X, 담기 Y, 담기 Z]`가 현재는 X를 경험 상품에 넣는다. (가)를 택하면 X가 빠지고 벡터가 `정규화(vY + vZ)`여야 한다. `[삭제 X, 주문 X, 담기 X, 담기 Y]`에서는 X가 남아야 한다(주문 보존).
- **API 영향**: 형식 변화 없음. (가)를 택하면 개인화 추천 응답의 내용이 달라진다
- **예상 변경 파일**: `UserProfileEmbeddingService.java`, `UserProfileEmbeddingServiceTest.java`(또는 새 테스트), B-4 문서
- **예상 변경 라인 수**: 코드 30~50줄, 테스트 60~100줄
- **위험도**: Low(코드) · 정책 선택 필요(제품)
- **테스트 영향도**: 기존 7건은 계산 함수만 고정해 영향 없음. 새 테스트가 B-3 공백을 메운다
- **예상 효과**: 승인된 정책과 동작 일치, 로그 → 프로필 경로의 첫 테스트

## ✅ B. 유지보수성 향상을 위한 리팩토링

### B-1. 갱신 스킵 게이트가 걸러내기 전 로그 수를 센다

- **Priority**: Medium
- **Category**: Architecture
- **문제**: 로그가 3건 미만이면 취향 벡터를 만들지 않는 갱신 스킵 게이트가, 비중 0 로그를 걸러내기 **전의** 로그 수로 판정한다(`:99`). 같은 상품의 로그 3건도 통과한다.
- **근거**: `[담기 X, 수량 변경 X, 수량 변경 X]`이면 조건을 통과하고 취향 벡터가 X의 벡터 그 자체가 된다. `[담기 X, 삭제 Y, 삭제 Z]`도 상품 1개짜리 취향이 된다. 이미 담긴 상품을 다시 담아도 수량만 합쳐지고 `CART_ITEM_ADDED`는 발행된다(`Cart.java` `addItem`, `CartService.java:57`).
- **왜 문제인가**: 스펙의 "로그 3개"와 문자 그대로는 일치한다. 하지만 이 조건을 둔 이유("1~2건만으로 분석하면 방금 담은 상품과 비슷한 것만 추천된다", `features/taste-vector.md:81`)를 코드가 막지 못한다. 값 3 자체의 근거도 없다(D-1 표).
- **개선 방법**: "사용할 수 있는 서로 다른 상품 수"로 셀지, 로그 수를 유지하고 이유 설명을 고칠지 결정한다. A-1과 함께 정한다(판단 2번).
- **검증 방법**: 위 두 조합을 mock으로 넣어, 수정 후 빈 결과가 나오는지 본다.
- **API 영향**: 형식 변화 없음
- **예상 변경 파일**: `UserProfileEmbeddingService.java`, 테스트, 스펙 규칙 표
- **위험도**: Low

## 💡 C. 참고 사항 (이번엔 수정하지 않음)

- **C-1. 같은 상품의 로그가 많을수록 비중이 커진다.** 로그마다 합산하므로 담기 뒤 주문한 상품은 3 + 2 = 5가 된다. 재현 R2에서 `[주문 P, 담기 P, 담기 Q]`의 P:Q 비율이 2.5였다. 수량을 **줄여도** +1이 붙고, 한 상품을 여러 번 조작하면 10칸 창을 채워 창 안의 주문을 밀어낼 수 있다. 지금 안 하는 이유: 프론트가 수량 버튼을 누를 때마다 `updateQuantity`를 부르는지 알 수 없고 `[미정]`, 개인화 추천을 평가할 정답 데이터(골든셋)가 없어 "상품당 한 번만 센다"가 더 나은지 판정할 수 없다(`full-module/002:237`).
- **C-2. 같은 주문 확정이 두 번 발행될 수 있다.** `InventoryConfirmedConsumer.java:53-54`의 조기 반환도 정상 반환이라, `HistoryAspect`가 이벤트를 그대로 발행한다. baro-ai의 중복 방지는 메시지 위치(`{파티션}-{오프셋}`)만 보므로 같은 주문이 두 번 오면 비중 6이 되고 창을 2칸 차지한다. 지금 안 하는 이유: 빈도를 모르고 재현한 적이 없으며, 원인이 baro-order 쪽(STOP §0 밖)이다.
- **C-3. 장바구니 비우기는 이벤트가 없다.** `clearCart`에 `@TrackHistory`가 없어, 비운 상품의 담기 로그가 남는다. 증상은 A-1과 같지만 원인이 발행 쪽이다. 지금 안 하는 이유: 다른 모듈 수정이 필요하고, 프론트가 비우기와 개별 삭제 중 무엇을 쓰는지 알 수 없다 `[미정]`.

## 🚫 D. 수정하지 않는 것이 더 좋은 사항

### D-1. 가중치 숫자를 지금 다시 정하기

평가 수단 없이 바꾸면 근거 없는 값을 다른 근거 없는 값으로 바꾸는 것에 그친다. 결과에 작동하는 것은 비율 3:2:1과 0뿐이다. 근거 조사 결과는 아래와 같다. `full-module/002`의 "직관" 분류는 사실이다.

| 값 | 처음 들어온 곳 | 기록된 근거 |
|---|---|---|
| 3 / 2 / 1 / 0 | `1097ca7f`·`66e00966` (2026-01-12, #103) | 한 줄 주석("관심 표현·유지·감소", "가장 높은 관심")뿐. 측정·실험 기록 없음. 테스트는 값을 고정만 한다 |
| 최소 3건 | `1097ca7f` | 없음 (`full-module/002:249`) |
| 최근 10건 | 옛 "유형별 5건 × 2" | 5 자체의 근거 없음 (`full-module/002:250`) |
| 30일 | 최초 커밋 | 없음 (`full-module/002:251`) |

이 숫자는 원래 "상품명을 텍스트에 몇 번 반복해 넣을지"를 정하는 반복 횟수였다. 2026-09-05 재설계로 벡터 가중 평균의 비중이 되면서도 값은 그대로 옮겨졌다(`taste-vector-pipeline.md:185` "전부 이전과 같다"). 쓰임새가 바뀐 뒤 다시 따져 본 기록은 없다.

### D-2. 삭제를 음수 비중으로 표현하기

가중합에 음수 항이 들어가면 취향이 뺀 상품의 **반대 방향**으로 기운다. "관심 없음"이 아니라 "반대 성향을 좋아함"이라는 다른 뜻이 된다. 창 안에 담기 로그가 없는 삭제도 취향을 밀어내게 된다.

### D-3. `case ORDER_CANCELLED` 삭제

switch가 모든 경우를 다뤄야 컴파일되므로, 이 case를 지우면 `default`가 필요해진다. `taste-vector/001` A-1(모든 가중치가 1이 된 사고)을 만든 조용한 기본값 처리가 되돌아온다.
