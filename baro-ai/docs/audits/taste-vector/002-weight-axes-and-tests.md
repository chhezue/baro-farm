# Taste-vector Architecture Audit 002 — 가중치 3축의 실효성·단위 테스트 (2026-09-06)

취향 벡터 작업 단위의 가중치 계산(`UserProfileEmbeddingService`의 행동 × 수량 × 시간 세 축)을 2026-09-06 비판 평가에서 수식과 상수로 다시 검산한 결과다. 코드에서 나오는 사실 3가지(시간 축이 흔한 경우 상수로 붕괴, 감쇠가 23일에 바닥, 유효 가중치 범위 150배)를 확인했지만 **어느 것도 A로 매기지 않았다** — 고치는 방향이 전부 정책이라 판단 항목으로 넘긴다. B 항목은 가중치 함수를 테스트 가능하게 만들고 테스트를 붙이는 2건이며, 판단 항목 1은 (가) 삭제로 결정돼 **전부 반영 완료**(2026-09-06)다.

- 기준: `audit-checklist.md` 1~16항목, `core-guardrails.md` ⛔ STOP §1(정책은 임의로 바꾸지 않는다)

## 확인한 사실 (정책 판단의 재료 — 등급 없음)

세 가지 전부 `UserProfileEmbeddingService.java`의 상수와 수식에서 그대로 나온다. 재현: 아래 값을 계산기에 넣으면 된다.

| # | 사실 | 근거 |
|---|------|------|
| F-1 | **흔한 경우 시간 축은 결과에 아무 영향이 없다.** 로그를 유형별 최근 5건만 읽는데(`:46` `RECENT_LOG_LIMIT = 5`, `:90`), 한 번의 쇼핑에서 5개를 담으면 5건이 같은 시간대다. 시간 가중치가 전부 같은 값(1시간 안이면 3.0)이 되고, 최종 벡터를 L2 정규화하므로(`:314` `normalized[i] = blended[i] / length`) 모든 항에 같이 곱해진 상수는 소거된다 | `:46`·`:90`·`:244-248`·`:301-316` |

### B-2. 가중치·정규화 단위 테스트

- **Priority**: High
- **Category**: Architecture (테스트성)
- **문제**: 취향 벡터의 정확성을 결정하는 수식이 검증 없이 있다
- **근거**: 테스트 0개. `001`도 "가중치 함수는 순수 함수라 테스트를 들일 때 첫 대상"이라고 적었다(`001:16`·`:254`)

- **개선 방법**: `UserProfileEmbeddingServiceTest`(순수 JUnit, Mock 없음). 테스트 이름이 F-1~F-3을 문장으로 고정한다:
  - 행동 가중치 4종(주문 3·담기 2·수량변경 1·삭제·취소 0)
  - 수량 `null → 1`, `0 → 1`, `100 → 5`(상한)
  - 시간: 0시간 → 3.0, 168시간 → 1.5(반감), 558시간 이상 → 0.3(하한), 미래 시각 → 3.0(상한)

  - 범위: 최대/최소 조합이 45와 0.3인지(F-3을 숫자로 못 박음)

- **예상 변경 파일**: `src/test/java/com/barofarm/ai/embedding/application/UserProfileEmbeddingServiceTest.java`

## 💡 C. 참고 사항 (권장하지만 이번엔 수정하지 않음)

### C-1. 저장 직후 조회가 최신 로그를 놓칠 수 있다

검색·장바구니 로그를 `save`한 뒤 별도 스레드에서 프로필을 재계산하는데, Elasticsearch는 기본 1초 refresh 간격이라 방금 쓴 문서가 바로 검색되지 않을 수 있다. 그러면 이번 갱신은 직전 상태로 계산되고 다음 행동에서 따라잡는다. 지금 하지 않는 이유: 갱신은 행동마다 반복되므로 1건 지연은 자연 회복되고, 강제 refresh는 쓰기 비용을 키운다. 키워드 검색 `002` A-1(검색 로그 비동기화)을 구현할 때 순서가 어떻게 되는지만 확인한다

## 판단이 서지 않는 항목

1. **시간 축을 어떻게 할 것인가.** F-1·F-2에 따라 지금 구조에서 시간 감쇠는 대부분 효과가 없다. 선택지:
   - **(가) 시간 축 삭제** — 상수 3개·메서드 1개가 사라지고 가중치가 행동 × 수량 두 축(범위 1~15)으로 단순해진다. 30일 창 밖은 이미 조회에서 걸러지므로 "오래된 건 덜 본다"는 의도는 창 자체가 담당한다. 가장 단순
   - **(나) `RECENT_LOG_LIMIT`를 늘려 시간 축이 작동할 재료를 준다**(예: 20) — 시간 축은 유지하되 여러 날의 로그가 섞이게 한다. 조회량이 4배가 되고, F-3의 범위 문제는 그대로 남는다
   - **(다) 유지** — 문서에 "흔한 경우 시간 축은 무효"라고 사실만 적는다
   기본 제안은 **(가)**다 — 이 이니셔티브의 원칙("잰 적 없는 복잡도는 걷어낸다")과 맞고, 되돌리기도 쉽다(git). 사용자 결정
2. **F-3의 150배 범위가 의도인가.** 수량 상한 5는 승인된 결정이고, 행동 가중치 3/2/1도 스펙에 있다. 두 축의 곱이 15배까지 벌어지는 것을 그대로 둘지, 아니면 "주문 1건 ≈ 검색 N건"의 N을 정할지는 개인화 추천 골든셋이 생긴 뒤 재는 게 맞다. 지금은 **테스트로 숫자를 고정만** 하고 값은 바꾸지 않는 것을 제안한다
