# 포트폴리오 케이스 스터디 — baro-ai 4개 주제

[기능·기술 문서](../features/README.md)가 "무엇을 어떻게 만들었나"를 설명한다면, 이 묶음은 **주니어 백엔드 개발자의 포트폴리오·기술 면접 관점**에서 같은 4개 주제를 다시 쓴 것이다. 네 편 모두 `문제 → 해결 → 대안 → 트레이드오프 → 결과 → 회고`라는 같은 6단계를 지키고, 각 단계의 주장에는 코드·측정·감사 문서 중 하나를 근거로 붙인다.

자랑이 아니라 **판단의 기록**이라, 기각된 자기 가설과 리뷰어가 잡은 결함도 그대로 적는다.

## 언제 이 문서를 보는가

- 이력서·포트폴리오의 "기여 내용" 항목을 쓸 때 — 각 편의 1·5절이 그 초안이다
- 면접에서 "왜 그렇게 했어요?"·"대안은요?"·"한계는요?"에 답할 때 — 3·4·6절이 그 답이다
- 6개월 뒤 같은 기능을 다시 손댈 때, 당시 무엇을 고민했는지 되짚을 때

## 한눈에 보기

| 주제 | 케이스 스터디 | 한 줄 | 핵심 숫자 |
|---|---|---|---|
| 장바구니 레시피 | [`cart-recipe.md`](cart-recipe.md) | 요청당 LLM 호출을 3회에서 1회로 옮기고, 프롬프트를 골든셋으로 판정해 고쳤다 | 합격률 69.0%→90.5% · 출력 토큰 −72.6% · 가설 2건 기각 |
| 개인별 추천 | [`taste-vector.md`](taste-vector.md) | 옆 모듈과의 문자열 불일치로 전부 1이던 가중치를 고치고, 근거 없는 축 2개와 신호 1개를 지웠다 | 원격 호출 6회→4회(임베딩 0) · 비중 범위 150배→3배 · 비동기 폐기 693건→0건 |
| 임베딩 검색 | [`vector-similarity.md`](vector-similarity.md) | "HNSW로 바꿔야 한다"를 3단계 실측으로 재고 **바꾸지 않았고**, 벡터 차원은 절반으로 줄였다 | 1만 건 p95 7.4ms(전환 불필요) · 같은 카테고리 45%→11.5% · p95 183ms→52.7ms |
| 검색 | [`keyword-search.md`](keyword-search.md) | 존재하지만 동작하지 않던 오타 검색·캐시를 살리고, 색인을 묶음으로 바꿨다 | 문서당 21KB→371B · bulk 4.3배 · 1건씩 임베딩은 13회 뒤 429 |

읽는 순서는 위 표 순서를 권한다 — 앞의 두 편이 "무엇을 잘못 만들었나", 뒤의 두 편이 "무엇을 재고 안 바꿨나"에 가깝다.

## 네 편 공통 목차 — 6단계

| 절 | 무엇을 답하나 |
|---|---|
| **1. 수행한 문제 (Problem)** | 기존 동작과 병목·결함, 그 증상, 사용자·인프라에 미치던 실제 영향 |
| **2. 해결 방법 (Solution)** | 사실을 확인한 방법(코드 역추적·수식 검산·부하 측정)과 아키텍처·코드 수준의 개선, 그리고 장애 격리·폴백 설계 |
| **3. 기술 선택 및 대안 (Alternatives & Technical Choices)** | 후보 대안 / 검토 이유 / 채택하지 않은 이유 / 최종 선택과 근거 — 흔히 쓰는 기술을 왜 안 썼는지 포함 |
| **4. 트레이드오프 (Trade-offs)** | 얻은 것과 대가로 내준 것. "무엇도 잃지 않았다"는 답은 쓰지 않는다 |
| **5. 결과 (Results)** | Before/After 표. 성능 지표·코드 품질·테스트 검증 결과 |
| **6. 회고 및 향후 개선 과제 (Retrospective & Future Work)** | 배운 것, 다시 한다면, 그리고 다음 단계의 구체적 계획 |

숫자는 전부 이 저장소의 실측 자료에서 왔다. 원본은 각 편이 링크하는 [`audits/`](../audits/README.md)의 감사 문서·벤치마크 JSON·골든셋 채점표에 있다. **재지 않은 것은 "재지 않았다"고 적는다.**

## 공통 회고 — 주제를 가로지르는 것

### 1. "일반적으로 좋다"를 근거로 쓰지 못하게 한 것이 가장 큰 차이를 만들었다

이 리팩터링 이니셔티브의 규칙은 **코드로 확인 가능한 사실이나 재현 가능한 측정**만 A(반드시 수정) 항목의 근거로 인정한다([`baro-ai-performance-refactor.md`](../../../.claude/rules/baro-ai-performance-refactor.md)). 그 규칙 때문에 세 가지가 일어났다.

- **바꾸지 않은 것이 생겼다.** HNSW 전환(1만 건에서 이득 0), 기본 양념 목록 확대(50%→45%, 잡음), 재료명 변종 통합(개선 없음), 공유 실행자 A안(응답 p95 7.5배 악화). 넷 다 "보통 이렇게 한다"였고, 재보니 아니었다.
- **판정 규칙을 재기 전에 적게 됐다.** "1만 건 p95 50ms 미만이면 전환 안 함", "중복률 −10pp 이상이고 유사도 손실 0.05 미만이면 다양화 유지". 결과를 보고 규칙을 만들면 언제나 "효과 있음"이 나온다.
- **측정 도구가 남았다.** 골든셋 실행기, 벡터 벤치마크(`scripts/vectorbench/`), 비동기 큐 벤치(`scripts/localbench/`), 다양화 측정. 다음에 같은 질문이 생기면 같은 조건으로 다시 잰다.

### 2. 내가 놓친 결함을 별도 컨텍스트의 리뷰어가 두 번 잡았다

같은 대화에서 짠 코드를 스스로 평가하면 자기 판단을 재확인하게 된다. 그래서 매 변경마다 신선한 컨텍스트의 리뷰어를 돌린다. 이번 라운드에서 실제로:

- **`_msearch` 부분 실패** — Spring Data ES가 실패한 항목을 빼고 자리를 당겨, 상품 카드가 엉뚱한 재료에 붙을 수 있었다. 리뷰어가 라이브러리 소스를 열어 확인했다.
- **Kafka 묶음 소비의 부분 실패** — 처음 구현은 하나가 실패하면 묶음 전체를 재시도하고 그래도 안 되면 **멀쩡한 뒤쪽 이벤트까지 버렸다.** 1건씩 처리하던 때보다 퇴행이었다. spring-kafka 소스로 확인됐다.

둘 다 "동작은 하는데 특정 실패에서만 틀리는" 종류라 테스트 없이는 운영에서 처음 드러났을 것이다. 반대로 **리뷰어의 지적을 실측으로 기각한 경우도 있다** — "ES refresh 경합으로 마지막 행동이 반영되지 않는다"는 A급 지적은 로컬에서 두 번 재현을 시도했으나 재현되지 않아 코드를 고치지 않았다.

### 3. 테스트 0개에서 59개로 — "유의미한 것만"의 실제 모양

저장소에 테스트가 하나도 없었다(`./gradlew :baro-ai:test`가 `NO-SOURCE`였다). 순수 계산(재료 정규화, 가중치, 코사인·다양화)과 서비스 경계(이유 코드, multi-search 1회, 묶음 색인, 폴백)를 대상으로 10클래스 59건을 들였다. 기준은 "인프라 없이 돌고, 깨지면 사용자에게 보이는 것"이다.

시간 축을 뺀 근거(같은 배수는 L2 정규화에서 소거된다)를 `blend_uniformScalingCancelsOut`이라는 테스트 이름으로 남긴 것처럼, **설계 판단 자체를 테스트로 고정한** 것이 몇 개 있다. ES·Kafka·Gemini가 필요한 통합 테스트는 아직 없다 — 그건 이 묶음의 공통 한계다(대신 로컬에 실제 인프라를 띄운 수동 통합 확인을 두 차례 했다).

### 4. 솔직한 자평 — 어디가 주니어 수준을 넘고 어디가 평범한가

| 넘는다고 생각하는 것 | 평범하거나 부족한 것 |
|---|---|
| 바꾸지 않은 결정에 3단계 실측 근거가 있다 | 통합 테스트가 없다 — 통합 검증은 사람이 손으로 돌린 수동 확인이다 |
| 측정 도구를 만들고 원본 JSON을 남겼다 | 개인화 추천의 **품질**은 한 번도 재지 않았다 — 골든셋이 없다 |
| LLM 출력의 신뢰 경계를 스키마·서버 계산으로 그었다 | 알고리즘 자체는 교과서적이다(가중 평균, max-min, script_score) |
| 실패 처리에 이유 코드·부분 실패 격리가 있다 | 관측(지연·큐 깊이·폐기 건수)이 Actuator 기본값 수준이다 |
| 프롬프트 변경을 사전 정의 5축 골든셋으로 판정했다 | 채점을 사람이 해서 84건이 상한이다 — 규모가 커지면 방법을 바꿔야 한다 |

### 5. 다시 한다면

- **측정 도구를 먼저 만든다.** 리팩터를 두 라운드 하고 나서야 골든셋을 만들었다. 채점식을 지운 전후 비교 자료가 없는 이유다.
- **테스트를 첫 라운드에 들인다.** 순수 함수 테스트는 인프라가 없어도 됐는데 "나중에"로 미뤘다.
- **로컬 인프라를 첫날에 세운다.** 실행자 포화(유실 37~65%)와 부족 재료 카드가 비는 원인은 둘 다 앱을 실제로 띄운 뒤에야 보였다.
- **발행 모듈 규칙을 먼저 읽는다.** 가중치 문자열 불일치, 취소 이벤트 미발행, `quantity` 의미 차이는 전부 옆 모듈 코드를 읽어야 보이는 것이었다.
