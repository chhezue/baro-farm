# 포트폴리오 케이스 스터디 — baro-ai 4개 주제

[기능·기술 문서](../features/README.md)가 "무엇을 어떻게 만들었나"를 설명한다면, 이 묶음은 **주니어 백엔드 개발자의 포트폴리오 관점**에서 같은 4개 주제를 다시 쓴 것이다 — 어떤 문제가 있었고, 무엇을 분석했고, 어떤 대안 중에 왜 이걸 골랐고, 무엇을 해결했고, 무엇이 아직 안 되고, 그걸 어떻게 풀 수 있는지, 그리고 하면서 무엇을 배웠는지. 자랑이 아니라 **판단의 기록**이라, 실패한 가설과 리뷰어가 잡은 결함도 그대로 적는다.

## 언제 이 문서를 보는가

- 이력서·포트폴리오의 "기여 내용" 항목을 쓸 때 — 각 케이스 스터디의 첫 절이 그 초안이다
- 면접에서 "왜 그렇게 했어요?"·"한계는요?"에 답할 때
- 6개월 뒤 같은 기능을 다시 손댈 때, 당시 무엇을 고민했는지 되짚을 때

## 읽는 순서

1. 이 문서의 **한눈에 보기** 표 — 4개 주제의 핵심 숫자
2. 관심 있는 주제의 케이스 스터디 — 각 편은 같은 절 순서를 지킨다
3. 이 문서의 **공통 회고** — 주제를 가로지르는 배움

|---|---|---|---|

## 케이스 스터디의 절 구성

포트폴리오 케이스 스터디 형식(맥락 → 문제 → 과정 → 해법 → 결과)에 이 저장소가 중시하는 두 가지 — **대안 중 왜 이걸 골랐는가**, **한계를 어떻게 풀 수 있는가** — 를 더했다. 네 편 모두 같다.

표로 된 절("대안과 선택"·"해결한 것"·"한계와 풀 수 있는 방법")은 헤딩이 곧 표의 설명이라 별도 도입 문장을 두지 않는다.

| 절 | 무엇을 답하나 |
|---|---|
| 한 줄 요약과 숫자 | 이력서 한 줄이 될 문장 + 근거 숫자 |
| 배경과 문제 | 무엇이 왜 문제였나. 누가 어떤 피해를 보고 있었나 |
| 무엇을 분석했나 | 가설·코드 확인·측정 — 어떤 방법으로 사실을 확인했나 |
| 대안과 선택 | 후보 / 왜 안 했나 / 왜 이걸 골랐나 |
| 해결한 것 | Before / After |
| 완결성과 참신성 — 솔직한 자평 | 끝난 것과 안 끝난 것, 남들과 다른 점과 평범한 점 |
| 한계와 풀 수 있는 방법 | 한계 → 방법 → 왜 아직 안 했나 |
| 회고 | 배운 것, 다시 한다면, 면접에서 할 한 문장 |

## 공통 회고 — 주제를 가로지르는 것

### 1. "일반적으로 좋다"를 근거로 쓰지 못하게 한 것이 가장 큰 차이를 만들었다

이 리팩터링 이니셔티브의 규칙은 **코드로 확인 가능한 사실이나 재현 가능한 측정**만 A 항목의 근거로 인정한다([`baro-ai-performance-refactor.md`](../../../.claude/rules/baro-ai-performance-refactor.md)). 그 규칙 때문에 세 가지가 일어났다.

- **바꾸지 않은 것이 생겼다.** HNSW 전환(1만 건에서 이득 0), 양념 목록 확대(50%→45%, 잡음), 재료명 변종 통합(개선 없음). 셋 다 "보통 이렇게 한다"였고, 재보니 아니었다.
- **결론 규칙을 재기 전에 적게 됐다.** "1만 건 p95 50ms 미만이면 전환 안 함", "중복률 −10pp 이상이고 손실 0.05 미만이면 유지". 결과를 보고 규칙을 만들면 언제나 "효과 있음"이 나온다.
- **측정 도구가 남았다.** 골든셋 실행기, 벡터 벤치마크, 다양화 측정 — 다음에 같은 질문이 생기면 같은 조건으로 다시 잰다.

### 2. 내가 놓친 결함을 리뷰어가 두 번 잡았다

같은 대화에서 짠 코드를 스스로 평가하면 자기 판단을 재확인하게 된다. 하네스는 그래서 별도 컨텍스트의 리뷰어(`spring-reviewer`)를 3파일 이상 변경에 강제한다([`core-tools.md`](../../../.claude/rules/core-tools.md)). 이번 라운드에서 실제로:

- **`_msearch` 부분 실패** — Spring Data ES가 실패한 항목을 빼고 자리를 당겨, 상품 카드가 엉뚱한 재료에 붙을 수 있었다. 리뷰어가 라이브러리 소스를 열어 확인했다.
- **Kafka 묶음 소비의 부분 실패** — 처음 구현은 하나가 실패하면 묶음 전체를 재시도하고 그래도 안 되면 **멀쩡한 뒤쪽 이벤트까지 버렸다.** 1건씩 처리하던 때보다 퇴행이었다. spring-kafka 소스로 확인됐다.

둘 다 "동작은 하는데 특정 실패에서만 틀리는" 종류라 테스트 없이는 운영에서 처음 드러났을 것이다.

### 3. 테스트 0개에서 61개로 — "유의미한 것만"의 실제 모양

저장소에 테스트가 하나도 없었다. 이번 라운드에서 순수 계산(재료 정규화, 가중치, 코사인·다양화)과 서비스 경계(이유 코드, multi-search 1회, 묶음 색인, 폴백)를 대상으로 10클래스 61건을 들였다. 기준은 "인프라 없이 돌고, 깨지면 사용자에게 보이는 것"이다. 시간 축을 뺀 근거(같은 배수는 정규화에서 소거된다)처럼 **설계 판단 자체를 테스트 이름으로 남긴** 것이 몇 개 있다. ES·Kafka·Gemini가 필요한 통합 검증은 아직 없다 — 그건 이 묶음의 공통 한계다.

### 4. AI 에이전트와 함께 일하는 방식 자체가 산출물이다

이 모듈은 규칙·스킬·훅·서브에이전트로 된 하네스 위에서 만들어졌다. 그 설계 배경과 실제 인시던트는 [`harness-engineering.md`](../harness-engineering.md)에 따로 있다. 여기서는 한 가지만 적는다 — **에이전트가 스스로 결정하지 못하게 한 지점**(무엇을 팔지, 시간 축을 뺄지, 다양화를 지울지, 커밋할지)이 있었기 때문에, 위 케이스 스터디의 "대안과 선택" 절에 사람이 내린 결정과 그 이유가 남아 있다.

### 5. 솔직한 자평 — 어디가 주니어 수준을 넘고 어디가 평범한가

| 넘는다고 생각하는 것 | 평범하거나 부족한 것 |
|---|---|
| 바꾸지 않은 결정에 근거가 있다(HNSW·양념·변종) | 통합 테스트·로컬 기동 검증이 없다 — "컴파일과 단위 테스트까지 확인된 상태" |
| 측정 도구를 만들고 원본을 남겼다 | 개인화 추천의 **품질**은 한 번도 재지 않았다 — 골든셋이 없다 |
| LLM 출력의 신뢰 경계를 스키마·서버 계산으로 그었다 | 알고리즘 자체는 교과서적이다(가중 평균, max-min, script_score) |
| 실패 처리에 이유 코드·부분 실패 격리가 있다 | 관측(지연·큐 깊이 지표)이 Actuator 기본값 수준이다 |
| 프롬프트 변경을 골든셋으로 판정했다 | 채점을 사람이 해서 84건이 상한이다 — 규모가 커지면 방법을 바꿔야 한다 |

### 6. 다시 한다면

- **측정 도구를 먼저 만든다.** 이번엔 리팩터를 두 라운드 하고 나서야 골든셋을 만들었다. 채점식을 지운 전후 비교 자료가 없는 이유다.
- **테스트를 첫 라운드에 들인다.** 순수 함수 테스트는 인프라가 없어도 됐는데 "나중에"로 미뤘다.
- **발행 모듈 규칙을 먼저 읽는다.** 가중치 문자열 불일치, 취소 이벤트 미발행, `quantity` 의미 차이는 전부 옆 모듈 코드를 읽어야 보이는 것이었다.
