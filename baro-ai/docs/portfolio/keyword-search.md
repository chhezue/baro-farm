# 케이스 스터디 — 검색: 동작하지 않던 것을 살리고, 색인을 묶음으로

기술 설명은 [`features/keyword-search.md`](../features/keyword-search.md)에 있다. 이 문서는 같은 기능을 **판단의 기록**으로 다시 쓴 것이다.

## 한 줄 요약과 숫자

**"있지만 동작하지 않던" 오타 검색·자동완성 캐시를 코드 근거로 찾아 살리고, 검색 응답에서 벡터를 빼 문서당 21KB→371바이트로 줄였으며, 상품 색인을 5건 묶음(임베딩 1회·bulk)으로 바꿔 무료 티어 한도(1건씩 13회 뒤 429)를 넘겼다. 묶음 소비의 부분 실패로 이벤트가 유실되는 결함은 리뷰에서 잡혀 실패 위치 기반 재시도로 고쳤다.**

| 숫자 | 뜻 |
|---|---|
| 21,160 → 371바이트 | 검색 히트 1건이 ES에서 앱으로 오는 크기 (벡터 제외) |
| 4.95초 → 1.16초 | 상품 1,000건 저장 (1건씩 vs bulk) |
| 13회 → 429 | 무료 티어에서 임베딩을 1건씩 보낼 때 막히는 지점. 10건 묶음은 통과 |
| 0 → 25건 | 이 단위의 단위 테스트 (그중 `multiSearch` 2건은 장바구니 레시피 라운드가 먼저 넣은 것) |

## 배경과 문제

검색은 baro-ai에서 가장 자주 불리는 API인데, 감사 전에는 세 가지가 "있는 척"만 하고 있었다.

1. **오타 검색이 동작하지 않았다.** `fuzziness`를 형태소 필드 전체에 걸어 검색어 "사과"와 "청송 꿀사과 부사 5kg" 사이 길이 차 때문에 한 글자 허용으로는 매칭 자체가 안 됐다.
2. **캐시가 아무 일도 안 했다.** `@Cacheable`은 있는데 `@EnableCaching`이 없었다. 있었더라도 기본 캐시는 크기·만료가 없어 무한히 쌓인다.
3. **검색 한 번에 필요한 것의 57배를 받아 왔다.** 화면에 쓰는 건 ID·이름·카테고리·가격인데 추천용 1536차원 벡터가 히트마다 딸려 왔다.

그리고 색인 경로는 상품 1건마다 외부 AI를 두 번 부르고 Kafka는 1건씩만 가져와서, 전량 재색인이 상품 수 × 3초였다. 재색인은 프롬프트를 고칠 때마다 필요한 작업이라(이번 주 2회) 가정이 아니라 예정된 병목이었다.

## 무엇을 분석했나

- **grep으로 사실 확인.** `@EnableCaching` 0건, `withSourceFilter` 0건 — "느릴 것 같다"가 아니라 "없다".
- **문서 크기 실측.** `GET product/_doc/{id}` 전체 21,160바이트, 벡터 제외 371바이트.
- **오타 매칭 재현.** 형태소 필드에 건 `fuzziness=1`이 왜 안 잡히는지 길이 차로 설명하고, 띄어쓰기 단위 서브필드에서 잡히는지 확인.
- **색인 병목 분해.** 상품 1건 = 임베딩 1회 + 재료명 LLM 1회 + ES 저장 2회 + poll 1건. 어느 항이 배치로 줄고 어느 항이 안 주는지 나눴다 — 임베딩·ES는 줄고, 재료명 LLM은 프롬프트 변경이라 별도 라운드.
- **한도 실측.** 무료 티어에서 임베딩 1건씩 13회 성공 뒤 429, 10건 묶음 5회 통과, 25건 이상은 분당 한도. 공식 문서에 배치 상한이 없어 재서 적었다.
- **최악 지연 산술.** 상품 1건 최악 = (30초 × 3회) × 2호출 = 180초. poll 처리 허용 15분 안에서 "최악에도 리밸런싱 없음"을 유지하는 최대 묶음은 5.

## 대안과 선택

| 결정 | 대안 | 왜 안 했나 | 선택과 이유 |
|---|---|---|---|
| 오타 매칭 | `fuzziness=AUTO`로 허용 폭 확대 | 두 글자 검색어에서 엉뚱한 상품을 대량으로 끌어옴 | 띄어쓰기 단위 서브필드 + 한 글자 + 첫 글자 고정 |
| 캐시 | Redis 도입 | baro-ai에 없는 인프라. 이 트래픽에서 정당화 불가 | Caffeine 로컬, 자동완성만(1,000개·5분). 검색 결과는 적중률 낮고 5분 지연을 허용하기 어려움 |
| 색인 처리량 | 앱 안 스레드풀로 병렬화 | 오프셋 커밋과 처리 완료가 어긋난다. Kafka의 방식은 파티션·컨슈머 수 | poll 5건 묶음 리스너 + 임베딩 배치 + `saveAll` |
| 묶음 크기 | 10건 + 처리 허용 늘리기 | 처리 허용을 늘리면 실제로 죽은 컨슈머를 알아채는 데 그만큼 오래 걸린다 | 5건·15분 — 최악 지연 산술에서 나온 최대값 |
| 검색 로그 | 응답 후 동기 저장 유지 | 부가 데이터 쓰기가 주 응답을 붙잡는다 | 로그+갱신을 비동기 작업 하나로. 큐 초과 시 로그 유실 허용(다음 행동에서 재계산) |

## 해결한 것

| 항목 | Before | After |
|---|---|---|
| 오타 검색 | 존재하나 매칭 불가 | `productName.word`, 한 글자, `prefixLength=1` |
| 자동완성 두 단어 | 결과 없음(이중 접두어 확장) | `match(and)` 단일 |
| 캐시 | no-op | Caffeine 1,000개·5분, 자동완성만 |
| 검색 히트 크기 | 21KB | 371B |
| 페이징 | 무제한 | `size` ≤100, `(page+1)×size` ≤10,000 → 400 |
| 색인 | 1건씩, 임베딩 1건씩 | 5건 묶음, 임베딩 묶음 1회, bulk |
| 묶음 부분 실패 | (처음 구현) 묶음 전체 재시도 후 전부 폐기 | 실패 위치 담아 던짐 → 앞은 커밋, 그 자리부터 재시도 |
| 검색 로그 쓰기 | 응답 스레드 동기 | 비동기 작업 1개 |

## 완결성과 참신성 — 솔직한 자평

**완결성.** 조회 경로는 스펙·감사·테스트·문서가 다 맞물려 있다. 색인 경로는 코드와 단위 테스트까지는 됐지만 **로컬 Kafka로 묶음 리스너를 실제로 돌려 보지 못했다** — 위치 기반 재시도 동작은 spring-kafka 소스와 리뷰어 확인에 기대고 있다. 로컬 ES에 nori가 없어 앱 자체를 띄운 검증도 아직이다.

**참신성.** 기법 자체(서브필드 fuzzy, Caffeine, 배치 리스너)는 평범하다. 다른 점이 있다면 두 가지 — (1) "있지만 동작하지 않는" 것을 grep과 실측으로 찾아 근거를 붙였다는 것, (2) 묶음 크기를 "적당히 10"이 아니라 최악 지연 산술로 정하고, 그 산술의 전제(1건 때의 안전 보장 유지)를 적었다는 것.

## 한계와 풀 수 있는 방법

| 한계 | 풀 수 있는 방법 | 왜 아직 안 했나 |
|---|---|---|
| 재료명 LLM이 상품당 1회라 재색인 시간의 대부분이 그대로 | 상품 N개를 한 프롬프트로 | 프롬프트가 바뀌어 골든셋(17/17)을 다시 재야 한다. 별도 라운드 |
| 상태·가격만 바뀐 수정에도 임베딩·LLM 재호출 | 발행 측이 변경 필드를 보내거나, baro-ai가 상품명 변경 여부로 건너뛰기 | 수정 이벤트 빈도 `[미정]` — 얼마나 낭비인지 모른다 |
| `updatedAt`이 발행 시각이라 재발행 시 최신순이 뭉개짐 | 발행 측이 상품 변경 시각을 보낸다 | 발행 모듈 담당자 확인 대기 |
| 상품 이벤트에 키가 없어 순서 미보장 | 발행 측이 상품 ID를 키로 | 발행 모듈 변경 |
| 통합 검증 없음 | nori 이미지 + Kafka 로컬 기동, 상품 100건 재발행 Before/After | 인프라 묶음(`open-items.md` A절) |
| 백그라운드 풀 하나를 프로필 갱신과 검색 로그가 공유 | 풀을 둘로 분리 | 검색 대비 장바구니·주문 이벤트 비율과 폐기 빈도를 잰 적이 없다 |
| Gemini 무료 티어로 전량 재색인이 가능한지 모름 | 상품 총수 확인 후 티어 결정 또는 묶음 크기 조정 | 상품 수 `[미정]` |

## 회고

- **"기능이 있다"와 "기능이 동작한다"는 다르다.** 오타 검색·캐시 둘 다 코드에 있었다. 확인하는 데 든 건 grep 두 번과 curl 한 번이었다.
- **배치 크기는 성능 숫자가 아니라 실패 시나리오에서 나온다.** 5를 고른 이유는 "빠르다"가 아니라 "최악에도 리밸런싱이 안 난다"였다. 그리고 그 실패 시나리오를 리뷰어가 한 단계 더 파서(부분 실패 시 유실) 결함을 잡았다 — 내가 "묶음 전체 재시도"까지만 생각하고 "그 뒤 전부 폐기"를 안 본 것이다.
- **한도는 문서가 아니라 실측이 알려 줬다.** 배치의 실익이 속도가 아니라 429 회피라는 건 재보기 전엔 몰랐다.
- **비동기로 옮긴 것과 논블로킹은 다르다.** 검색 로그를 별도 스레드로 넘겼지만 그 안의 Elasticsearch 쓰기는 여전히 스레드를 붙잡는다. 응답에서 뺐을 뿐 서버가 쓰는 자원의 총량은 그대로고, ES가 느려지면 스레드 2개가 다 묶인 뒤 대기열 100건이 차고 그때부터 로그가 버려진다. 정확히 말하면 **문제가 사라진 게 아니라 응답 지연에서 로그 유실로 형태를 바꿨다.** 형태를 고른 것이지 없앤 것이 아니다.
- **그래서 리액티브로 가지 않았다.** 스레드를 아예 안 붙잡으려면 논블로킹 클라이언트로 바꿔야 하는데, 이 서비스가 부르는 것(ES 클라이언트·Feign·Gemini SDK)이 전부 동기 블로킹이라 한 곳만 바꿔도 이득이 없다. 스레드 하나가 대기에 묶이는 구조는 그대로다.
- **면접에서 할 한 문장:** "묶음 크기 5는 상품 1건의 최악 지연 180초와 poll 처리 허용 15분에서 역산한 값이고, 묶음 안 부분 실패로 이벤트가 유실되는 결함은 리뷰에서 잡혀 실패 위치 기반 재시도로 고쳤습니다."
