# 케이스 스터디 — 장바구니 레시피: LLM을 어디까지 믿을 것인가

기술 설명은 [`features/cart-recipe.md`](../features/cart-recipe.md)에 있다. 이 문서는 같은 기능을 **판단의 기록**으로 다시 쓴 것이다. LLM은 Large Language Model(거대 언어 모델)이다.

## 한 줄 요약과 숫자

**요청 1회에 LLM을 3번(최악 N+3번) 부르던 구조를 "재료명은 상품의 속성"이라는 관찰로 색인 시점 1회로 옮겨 요청 경로를 1회로 줄였고, LLM 출력을 JSON 스키마 강제와 서버 측 재료 대조로 검증 경계 안에 가뒀다. 프롬프트는 골든셋(15종 중 LLM을 부르는 14종 × 3회 × 2팔 = 84건)으로 재서 고쳤고(합격 69.0%→90.5%, 토큰 −72.6%), 이후 세운 가설 2건은 측정으로 기각했으며, 진짜 병목이 프롬프트가 아니라 카탈로그(살 게 없는 추천 50%)임을 분류기로 보였다.**

| 숫자 | 뜻 |
|---|---|
| 3회 → 1회 | 요청당 LLM 호출 (최악 N+3 → 1) |
| 69.0% → 90.5% | 골든셋 실행 단위 합격률 (5축 전부 통과) |
| −72.6% | 출력 토큰 (후보 3개·8필드 → 1개·3필드) |
| 50% → 10% | "살 게 없는 추천" — 김치·두부·장류만 팔면 |
| 16/17 → 17/17 | 색인 시점 재료명 추출 정확도 |

## 배경과 문제

이 기능은 LLM에 크게 기대는 유일한 요청 경로다. 감사 전 상태는 이랬다.

1. **LLM을 3번 직렬로 불렀다.** 상품명 정규화 → 재료 재검증 → 레시피 생성. 타임아웃이 없어 요청 스레드를 무기한 붙잡을 수 있었고, 1번이 실패하면 상품별 개별 호출로 폴백해 최악 N+3회.
2. **LLM이 "부족한 재료"까지 말하고 그걸 그대로 카드로 냈다.** 그 값이 곧 "이걸 사세요"인데, 모델이 공백 하나만 흘려도 재료가 조용히 사라지는 대조 로직이었다.
3. **프롬프트가 억지 요리를 만들 압력을 주고 있었다.** "서로 다른 조리 방식으로 3개"를 요구해 마땅한 요리가 하나뿐인 장바구니에서 "오이 파스타"가 나왔다. 서버는 첫 후보만 쓰고 나머지는 버렸다. 판매 유도는 "부족 재료 30~50%"라는 비율이라 재료를 끼워 넣었다.
4. **과거의 판단이 기록에 없었다.** "할루시네이션이 심해 후보를 3개로 늘렸다"는 관찰이 어디에도 남지 않아 다시 판단할 근거가 없었다.

## 무엇을 분석했나

- **호출 시퀀스를 파일·라인 단위로 추적.** 정상 3회·최악 N+3회, 전부 직렬, 타임아웃 없음.
- **입력 의존성 분석.** 앞의 두 호출은 입력이 상품명·카테고리뿐 — 사용자·시점과 무관하다. "같은 계란을 100명이 담으면 같은 계산을 100번 했다." 이건 캐싱 관습이 아니라 구조적 사실이다.
- **카탈로그 확인.** 카테고리 22개가 전부 `AGRI_*`라 "비식재료를 걸러내자"는 2번 호출의 전제 자체가 성립하지 않았다.
- **골든셋 설계.** 장바구니 15종, 합격 5축(실재성·재료 정합성·보유 활용·조리법 타당성·판매 연결), 사람 채점(LLM 채점의 자기 편향 회피), 3회 반복(temperature 0.7이라 흔들림 흡수). 재기 전에 스펙에 확정.
- **1차 측정에서 회귀를 발견하고 규칙을 고쳐 재측정.** "쌀·보리"가 부족 재료 0개로 돌아가 판매 연결이 깨졌다 → 규칙 3을 "재료를 끼워 넣지 말고 요리 선택을 바꿔라"로.
- **가설 2건을 측정으로 기각.** 양념 목록 확대(50%→45%, 42건 중 2건), 변종 통합(개선 없음). 모델이 양념 규칙 자체를 20건 어긴다는 부수 관찰.
- **부족 재료를 코드로 분류.** 손으로 세던 41%·48%에 "다진마늘"을 양념에 넣은 오차가 있어, 분류기를 만들어 양쪽 팔을 같은 기준으로 판정. 김치·두부·장류 추가 시 21/42 → 4/42.
- **재료명 추출 검증에서 내 개선안의 회귀를 스스로 잡음.** 17/17이었는데 허용 목록이 느슨했다 — 조이자 "포기김치→포기김치"가 드러났다. 기준을 `{김치, 배추김치}`로 고정하고 다시 17/17.

## 대안과 선택

| 결정 | 대안 | 왜 안 했나 | 선택과 이유 |
|---|---|---|---|
| 재료명 계산 시점 | 요청 결과 캐시 | TTL·무효화 장치 필요. 상품이 바뀌면 이벤트가 어차피 온다 | 색인 시점에 상품 문서 필드로 |
| | 정규식 대체 | "대란"처럼 틀린 값이 정상 값처럼 저장됨 | 폴백 없음 — 빈 값은 "모른다"는 신호 |
| LLM 출력 신뢰 | 사용/부족 재료도 LLM에게 | 그 값이 구매 카드가 됨. 대조를 자주 틀림 | 서버가 정규화 비교로 계산. 스키마에서 그 필드 제거 |
| 응답 형식 | 프롬프트로 "JSON만" 부탁 | 코드펜스·설명 문장이 섞여 파싱 실패 | Gemini `responseSchema` 강제. 파싱 실패 catch는 유지 |
| 후보 수 | 채점식을 고쳐 억지 요리 걸러내기 | 압력의 원인(3개 강제)을 두고 결과만 거르는 것 | 후보 1개 + 문장 규칙. 채점식 삭제 |
| 판매 유도 | 비율(30~50%) 유지 | 개수를 맞추려 재료를 끼워 넣음 | "부족 재료 최소 1개", 완성되는 요리면 요리를 바꾸라 |
| 카탈로그 부족 | 프롬프트로 "카탈로그 안에서만" | 측정: 양념 목록도 20건 어김 — 목록을 지키지 않음 | 카탈로그 확장(사업 결정 — 사용자가 정함) |
| 실패 표현 | 예외(4xx) | 빈 장바구니는 오류가 아니라 사용자 상태 | 200 + `reason` 6종 |
| temperature | 전역 0.7 | 추출은 창작이 아님 — 같은 상품에 다른 재료명이 나옴 | 추출 호출만 0.0 |

## 해결한 것

| 항목 | Before | After |
|---|---|---|
| 요청당 LLM | 3회 (최악 N+3) | 1회 |
| 타임아웃·재시도 | 없음 | 호출당 30초, 총 3회 |
| 후보·출력 필드 | 3개·8필드 | 1개·3필드 |
| 골든셋 합격 | 69.0% | 90.5% |
| "오이 파스타" 재현 | 1/3 | 2/3 |
| 응답 `ownedIngredients` | 장바구니 전체 | 이 요리가 쓰는 보유 재료 (보유+부족=핵심) |
| 실패 5종 | 같은 빈 응답, 스택트레이스 없음 | `reason` 구분, 예외 객체 로깅 |
| 부족 재료 상품 검색 | 재료마다 순차 N회 | `_msearch` 1회 (부분 실패 시 순서 보호) |
| 재료명 프롬프트 | 농산물만 상정 | 김치·장류 예시 추가, 17/17 |

## 완결성과 참신성 — 솔직한 자평

**완결성.** 측정 → 결정 → 구현 → 문서가 한 바퀴 돈 유일한 단위다. 하지만 **결정된 카탈로그 확장이 아직 실행되지 않아** 부족 재료 카드는 여전히 대부분 비어 있고, 레시피 생성기 자체는 단위 테스트가 없다.

**2026-09-06 로컬 통합 확인에서 이 진단이 반쪽이었음이 드러났다.** 앱을 실제로 띄워 돌려 보니 카탈로그에 **있는** 상품도 연결되지 않았다 — 레시피가 "국거리용 소고기"를 요구했는데 `한우 등심 300g`(색인된 재료명 `소고기`)이 카드에 안 실렸다. 부족 재료 검색이 `productName`만 보고, 색인 시점에 뽑아 둔 `ingredientName`을 안 쓰기 때문이다. 즉 빈 카드의 원인은 카탈로그 하나가 아니라 **카탈로그 + 매칭 필드** 두 개였고, 뒤엣것은 코드로 지금 고칠 수 있다. 근거: [`audits/cart-recipe/006`](../audits/cart-recipe/006-missing-ingredient-product-match.md) A-1(승인 대기). 같은 확인에서 `_msearch` 묶음 조회와 `baro-shopping` 왕복(스텁)은 정상 동작을 확인했다.

**참신성.** "LLM 출력을 서버가 검증한다"는 이제 흔한 패턴이다. 다른 점은 (1) **어느 값을 LLM에게 묻지 않을지**를 "그 값이 구매 카드가 되는가"로 정한 것, (2) 프롬프트 변경을 사전 정의 5축·사람 채점·반복 3회로 판정한 것, (3) **자기 가설 두 개가 기각된 것을 그대로 남기고 코드를 바꾸지 않은 것**, (4) 자기 개선안의 회귀를 판정 기준을 조여 스스로 찾은 것. 마지막 둘이 이 포트폴리오에서 가장 드물다고 생각한다.

## 한계와 풀 수 있는 방법

| 한계 | 풀 수 있는 방법 | 왜 아직 안 했나 |
|---|---|---|
| 카탈로그 확장 미실행 | 카테고리 4행 SQL + 상품 시드 + 재색인 | SQL이 저장소 루트(하네스 쓰기 범위 밖). 배포·`baro-shopping` 담당자 |
| 게이트웨이가 `X-User-Id`를 검증하지 않음 — 남의 장바구니 조회 가능 | prod 라우트에 인증 필터 | 게이트웨이 담당자 확인 대기. 이 목록에서 가장 급한 항목 |
| 게이트웨이 5초 vs LLM 최악 90초 | 상한을 맞추거나 비동기 응답 | 어느 쪽에 맞출지 결정 전 |
| 사람 채점이라 84건이 상한 | 축 3·5는 이미 기계 판정. 축 1·2·4에 LLM 채점 + 사람 표본 검증 | 자기 편향 문제를 먼저 설계해야 함 |
| 채점식 삭제의 전후 자료 없음 | 없다 — 삭제 전 점수를 로그로 남기지 않았다 | 교훈으로만 남김("측정 도구를 먼저") |
| 재료명 LLM이 상품당 1회 | 여러 상품을 한 프롬프트로 | 골든셋 재측정 필요 |
| 생성기 테스트 없음 | `ChatClient`를 얇은 인터페이스 뒤로 | 파싱 실패 경로가 필요해질 때 |

## 회고

- **"어디서 계산하나"가 "얼마나 빨리 계산하나"보다 먼저다.** 캐시를 붙였다면 TTL·무효화를 얻었을 것이고, 색인 시점으로 옮기니 그 문제가 사라졌다. 입력 의존성을 보면 답이 나왔다.
- **프롬프트를 읽고 "위험해 보인다"로 고치지 말 것.** 세 번 시도해 두 번 빗나갔다. 이 저장소가 근거를 요구하는 이유를 몸으로 배웠다.
- **판정 기준이 느슨하면 측정이 회귀를 덮는다.** 17/17을 보고 끝냈다면 "포기김치"는 운영에서 발견됐을 것이다.
- **병목이 코드 밖에 있을 수 있다.** 프롬프트를 아무리 고쳐도 "살 게 없는 추천" 50%는 카탈로그가 정하는 숫자였다. 그리고 그건 개발자가 정할 일이 아니어서 결정을 넘겼다.
- **타임아웃은 개별 설정이 아니라 예산이다.** 이 경로 하나에 게이트웨이 5초, 장바구니 Feign 3초, ES 30초, LLM 30초×재시도 3회가 걸려 있고 전부 직렬이다. 안쪽 합이 바깥 상한을 넘으면 사용자는 이미 끊긴 뒤인데 서버 스레드만 계속 붙잡혀 있다. **블로킹 호출의 타임아웃은 곧 스레드를 붙잡는 시간이고, 그게 이 서버가 동시에 받을 수 있는 요청 수를 정한다.** 값 하나하나는 근거가 있지만 합을 맞춰 본 적이 없다는 게 이 단위에서 가장 부끄러운 부분이다.
- **면접에서 할 한 문장:** "LLM에게는 요리 이름·재료·조리법만 묻고, 구매 카드가 되는 '부족한 재료'는 서버가 계산합니다. 프롬프트는 골든셋 84건으로 판정해 합격률을 69%에서 90.5%로 올렸고, 그 뒤 세운 가설 두 개는 재보니 아니어서 코드를 바꾸지 않았습니다."
