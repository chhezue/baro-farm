# 케이스 스터디 — 임베딩 검색: 바꾸지 않기로 한 결정에 근거 붙이기

기술 설명은 [`features/vector-similarity.md`](../features/vector-similarity.md)에 있다. 이 문서는 같은 기능을 **판단의 기록**으로 다시 쓴 것이다.

## 한 줄 요약과 숫자

**"HNSW(Hierarchical Navigable Small World — 근사 최근접 탐색 그래프) 그래프를 만들어 놓고 안 쓴다"는 지적에 대해 상품 1천·1만·10만 건에서 지연을 실측해 "1만 건까지는 두 방식이 같다(p95 7.4ms)"를 확인하고 전환하지 않기로 결정했다. 다양화 알고리즘은 켜고 끈 결과를 실제 임베딩으로 비교해(같은 카테고리 쌍 45%→11.5%, 유사도 손실 0.036) 유지 근거를 만들었고, 벡터 없는 상품 1건이 추천 API 전체를 죽이던 결함을 필터로 고쳤다.**

| 숫자 | 뜻 |
|---|---|
| 7.4ms vs 6.4ms | 1만 건에서 `script_score` vs `knn` p95 — 같다 |
| 92ms vs 32ms | 10만 건에서 — 여기서 갈린다 |
| 45% → 11.5% | 추천 5개 중 같은 카테고리 쌍 비율, 다양화 OFF → ON(×3) |
| 1,030KB vs 2KB | k=30 응답, 벡터 포함 vs 제외 — 다양화의 가격 |

## 배경과 문제

벡터 검색 경로에는 세 가지 질문이 걸려 있었다.

1. **ES는 벡터를 저장할 때 근사 탐색 구조(HNSW)를 기본으로 만든다.** 우리 조회는 그걸 안 쓰고 필터 통과 문서를 전부 비교한다. "그러니 `knn`으로 바꾸자"는 자연스럽지만, 상품 수를 모른 채 바꾸면 "베스트 프랙티스라서"가 근거가 된다 — 이 저장소가 금지하는 근거다.
2. **다양화 알고리즘(199줄)은 비용이 확실하고 효과는 짐작이었다.** 후보 벡터를 전부 받아야 해서 요청당 최대 2MB인데, "골고루"가 실제로 얼마나 골고루인지 잰 적이 없었다.
3. **벡터 없는 상품이 하나라도 판매 중이면 추천 API가 빈 배열을 냈다.** `cosineSimilarity`는 벡터 없는 문서를 건너뛰지 않고 쿼리를 실패시키는데, 임베딩 실패는 정상 경로였다. 실패는 catch에 먹혀 "추천이 안 나온다"로만 보였다.

## 무엇을 분석했나

- **매핑이 실제로 무엇을 보내는지** Spring Data ES 5.3.6 jar 바이트코드로 확인 — `{"type":"dense_vector","dims":1536}`뿐이고 `index`·`similarity`는 서버 기본값(true·cosine). 즉 그래프는 이미 만들어진다.
- **클라이언트가 `knn`을 지원하는지** 같은 jar에서 확인 — 쿼리 DSL `knn` 절은 있고 최상위 `knn` 옵션 빌더는 없다.
- **결론 규칙을 먼저 적었다.** "1만 건 p95 50ms 미만이면 전환 안 함" / "중복률 −10pp 이상이고 유사도 손실 0.05 미만이면 다양화 유지". 결과를 보기 전에.
- **지연 벤치마크.** 난수 1536차원 벡터를 1천·1만·10만 건 넣고(10만 건 시드 9분), 운영과 같은 필터로 200회씩. 난수를 쓴 이유 — 지연은 문서 수·차원·구조에 의존하지 문서 값에 의존하지 않는다. 일치율만 실데이터와 다를 수 있어 참고값으로 표시.
- **다양화 측정.** 상품명 154개(14개 하위 카테고리)를 실제로 임베딩(무료 티어라 10개씩 7초 간격)하고, 기준 20개에 대해 OFF / ×2 / ×3 / ×5를 비교. 지표 셋 — 상호 거리, 같은 카테고리 쌍 비율, 기준과의 유사도(대가). 대가 없이 앞의 둘만 보면 항상 "효과 있음"이 나온다.
- **Python 구현이 Java와 같은지** 손으로 답을 낼 수 있는 3차원 예제(a, c, d)로 양쪽 다 확인.

## 대안과 선택

| 결정 | 대안 | 왜 안 했나 | 선택과 이유 |
|---|---|---|---|
| `knn` 전환 | 지금 전환 | 1만 건에서 이득 0. 근사라 결과가 정확 계산과 달라짐. 클라이언트 우회 코드 필요 | 유지. 분기점(수만~10만 건)과 재개 조건(nc=k×5, 실데이터 일치율)을 결정 기록에 적음 |
| | 그래프 생성 끄기(`index:false`) | 나중에 전환할 때 전량 재색인 필요. 그래프 비용은 조회 경로에 없음 | 남겨 둠 |
| | 상품 수 예상치를 물어 정하기 | 예상치 `[미정]`. 3단계를 다 재면 예상치 없이 결론이 남 | 3단계 실측 |
| 다양화 | 삭제 + 벡터 제외 수신(전송 535분의 1) | 같은 카테고리 45%로 돌아감 — 측정이 유지를 가리킴 | 유지 |
| | 배수 ×2 | 전송 3분의 2, 중복률 개선은 ×3보다 2.5~3.3pp 작음 | ×3 유지(규칙 안에서 효과 최대). 사용자 결정 |
| | 배수 ×5 | 유사도 손실 0.053 — 허용선 초과 | 기각 |
| 벡터 없는 문서 | 스크립트 안 `size()==0` 가드 | `exists` 필터가 있으면 중복 | `exists(vector)` 필터 |
| 고른 후보 판정 | `ProductDocument`에 `equals` 추가 | 엔티티 값 동등성에 벡터 배열 비교가 끌려옴 | `boolean[]` 인덱스 플래그 |

## 완결성과 참신성 — 솔직한 자평

**완결성.** 이 단위는 "바꾸지 않은 결정"이 핵심이라 코드 변경은 적고 문서·측정이 많다. 그 문서가 결정 기록·감사·스펙·Javadoc에 같은 숫자로 들어가 있다는 점에서는 완결됐다. 다만 **다양화 측정이 벤치용 상품명 기준**이고, 실제 카탈로그로는 재지 않았다.

**참신성.** 알고리즘은 교과서적이다 — 코사인 유사도, max-min 다양화(farthest-first 방식). 다른 점은 (1) 결론 규칙을 재기 전에 적은 것, (2) "전환하지 않는다"에 3단계 실측과 재개 조건을 붙인 것, (3) 다양화의 대가(유사도 손실)를 같이 재서 "효과 있음"이 자동으로 나오지 않게 한 것. 주니어 포트폴리오에서 "도입했다"보다 "재보고 안 했다"가 드물다고 생각한다.

## 한계와 풀 수 있는 방법

| 한계 | 풀 수 있는 방법 | 왜 아직 안 했나 |
|---|---|---|
| 일치율 수치가 난수라 최악 조건 | 실제 상품 벡터로 `knn_bench.py` 재실행 | 상품 시드가 없다. 지연 결론에는 영향 없음 |
| 다양화 측정이 벤치 상품명 기준 | 실제 카탈로그 임베딩으로 `diversity.py` 재실행 | 같은 이유 + Gemini 한도 |
| ~~1536차원이 필요한지 모름~~ | **2026-09-07 해소** — 768로 낮췄다 | 상위 5개 이웃 94.5% 보존, 동시 30 p95 183ms→53ms. 실제 적용은 재색인 뒤 |
| 분기점을 지켜보는 장치 없음 | `product` 문서 수 지표 + 알림 | 상품 수 자체가 `[미정]`이라 임계값을 못 정함 |
| 벡터 검색 지연 지표 없음 | Micrometer 타이머 1개 | 관측 항목 전반이 다음 라운드 |
| 요청당 후보 벡터 약 255KB(기본 topK) | 다양화를 ES 안에서 한다 | 차원 축소는 위 행에서 이미 했다(507KB→255KB). 남은 절반을 더 줄이려면 후보 벡터를 앱으로 가져오지 않는 구조여야 하는데, 그건 다양화 정책 자체를 바꾸는 일이다 |

## 회고

- **"만들어 놓고 안 쓴다"는 사실이지만 "그러니 써야 한다"는 아니었다.** 사실과 결론 사이에 측정이 있어야 한다는 걸 이 단위에서 가장 분명하게 배웠다.
- **대가를 같이 재지 않으면 측정이 편향된다.** 다양화는 상호 거리만 보면 ×5가 제일 좋다. 유사도 손실을 같이 보니 ×5는 허용선 밖이었다.
- **10만 건 벤치마크 시드에 9분이 걸렸다.** "1만 건까지만 재자"는 유혹이 있었고, 10만 건을 재서야 분기점이 어디인지 말할 수 있었다.
- **면접에서 할 한 문장:** "HNSW 전환은 1만 건에서 p95 7.4ms로 이득이 없어 하지 않았고, 다양화는 같은 카테고리 쌍 45%→11.5%에 유사도 손실 0.036이라 유지했습니다 — 둘 다 판정 규칙을 재기 전에 적었습니다."
