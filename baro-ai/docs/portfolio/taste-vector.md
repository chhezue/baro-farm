# 케이스 스터디 — 개인별 추천: 옆 모듈을 읽어야 보이는 결함들

기술 설명은 [`features/taste-vector.md`](../features/taste-vector.md)에 있다. 이 문서는 같은 기능을 **판단의 기록**으로 다시 쓴 것이다.

## 한 줄 요약과 숫자

**장바구니 행동 가중치가 발행 모듈과의 문자열 불일치로 전부 1이던 결함, `@Async` 자기 호출로 Kafka 리스너 스레드에서 동기 실행되던 결함, 깨진 메시지 1건이 파티션을 영구히 막던 결함을 감사에서 찾아 고쳤다. "상품명을 반복한 문장을 임베딩"하던 취향 벡터를 상품 벡터의 가중 평균으로 재설계해 행동 1건당 원격 호출 6회(ES 5 + Gemini 1)를 5회(ES만, 임베딩 0)로 줄였고, 계산은 하는데 결과에 영향이 없던 시간 감쇠 축을 계산으로 증명해 뺐다.**

| 숫자 | 뜻 |
|---|---|
| 임베딩 1회 → 0회 | 행동 1건당 원격 호출 6회(ES 5·Gemini 1) 중 Gemini 몫 — 이제 ES 조회 5회만 남는다 |
| 전부 1 → 3/2/1/0 | 장바구니 행동 가중치 (문자열 불일치 수정) |
| 150배 → 15배 | 비중의 유효 범위 (시간 축 삭제) |
| 23.3일 | 시간 감쇠가 하한에 닿던 시점 — 30일 창의 마지막 일주일은 평지였다 |

## 배경과 문제

이 단위는 세 모듈(`baro-shopping`·`baro-order`·baro-ai)에 걸쳐 있어 baro-ai 코드만 봐서는 문제가 안 보였다.

1. **가중치가 작동하지 않았다.** 컨슈머는 `"ADD"`를 저장하고 계산은 `"CART_ITEM_ADDED"`와 비교했다. 어떤 장바구니 로그도 `case`에 걸리지 않아 담기 2·삭제 0이 전부 1이었다. 문서는 "담기는 2배"라고 적혀 있었다.
2. **비동기가 비동기가 아니었다.** 컨슈머가 같은 클래스의 `@Async` 메서드를 불렀다. Spring 프록시는 자기 호출을 못 가로채니 임베딩 계산이 리스너 스레드에서 동기로 돌았다.
3. **취향 벡터 만드는 방식이 임베딩 모델의 계약이 아니었다.** "사과 사과 사과 바나나"를 임베딩하면 사과 쪽으로 3배 기울 거라는 가정. 행동 1건마다 원격 호출 6회(ES 조회 5 + Gemini 임베딩 1).
4. **깨진 이벤트 1건이 파티션을 막았다.** 역직렬화 보호도 에러 핸들러도 없었다.
5. **시간 감쇠 축이 계산만 하고 있었다.** (2차 감사) 종류별 최근 5건만 읽는 구조에서 한 번의 쇼핑 로그는 감쇠값이 같고, L2 정규화가 같은 배수를 소거한다.

## 무엇을 분석했나

- **발행 모듈 전수 조사.** `baro-shopping`의 `@TrackHistory` 3곳, `baro-order`의 주문 확정 1곳, `baro-common`의 `HistoryAspect`. 여기서 저장값·비교값 불일치(1번), 취소 이벤트 발행부 부재, `quantity`의 의미가 이벤트마다 다르다는 것(담기=증분, 수량 변경=새 총량, 삭제=전량)이 나왔다.
- **`@Async` 프록시 동작 확인.** 자기 호출 경로를 코드에서 추적. 별도 빈으로 분리.
- **가중치 3축을 수식으로 검산.** 하한 도달 시점 `168·log₂(10) ≈ 558시간 ≈ 23.3일`, 최대 45·양수 최소 0.3(150배), 정규화에 의한 전역 배수 소거. 계산기로 재현되는 사실만 적고 등급을 매기지 않았다 — 고치는 방향이 정책이라 사용자에게 넘겼다.
- **삭제 근거를 테스트로.** `blend_uniformScalingCancelsOut` — 모든 비중에 3을 곱해도 결과 벡터가 같다. 이 테스트가 통과하는 한 F-1이 성립한다.
- **가중치 함수를 테스트 가능하게.** private + 내부 `Instant.now()`라 잡을 수 없던 함수를 패키지 static으로.

## 대안과 선택

| 결정 | 대안 | 왜 안 했나 | 선택과 이유 |
|---|---|---|---|
| 취향 벡터 계산 | 반복 텍스트 임베딩 유지 + 캐시 | 가정 자체가 모델의 계약이 아님. Gemini 호출이 남음 | 로그 상품의 기존 벡터를 가중 평균 — 가중치가 수식 그대로 곱해짐, Gemini 호출 0 |
| 검색어 반영 | 검색어만 따로 임베딩 | 요청 경로에 임베딩 호출이 남음 | 상위 결과 상품 3개의 벡터에 검색 비중 → **2026-09-07 검색 신호 자체를 제거** |
| 비동기 | 같은 클래스 안에서 self-injection | 우회이고 읽는 사람이 오해 | 별도 빈 `UserProfileRefreshTrigger`, 유일한 진입점 |
| 큐 초과 | 기본 `RejectedExecutionException` | 컨슈머로 예외가 올라가 재시도 폭풍 | 로그 후 폐기 — 다음 행동에서 재계산 |
| 깨진 메시지 | DLT(Dead Letter Topic) | 취향 로그는 1건 유실 허용. DLT는 토픽·컨슈머·모니터링 비용 | `ErrorHandlingDeserializer` + 1초 2회 재시도 후 건너뜀 |
| 재시도 중복 | 중복 허용 | 같은 행동이 두 번 세어짐 | 문서 ID `{partition}-{offset}` — 덮어쓰기 |
| 수량 | 그대로 곱함 | 수량 100짜리 로그 하나가 프로필의 97% | 상한 5 → **2026-09-07 축 자체를 제거**(수량은 선호가 아니라 소비량) |
| 시간 축 | 로그 창을 20건으로 늘려 축을 살림 | 조회 4배, 150배 범위 문제 그대로 | 삭제(사용자 결정). 30일 창이 역할을 대신 |
| | 유지 + 문서에 "무효"라고 적기 | 계산만 하는 코드를 남김 | 삭제 |
| 카테고리 선호 | 유지 | 후보 선정에만 작용하고 정렬에서 사라짐. 벡터가 이미 그 방향 | 삭제 |

## 완결성과 참신성 — 솔직한 자평

**완결성.** 파이프라인의 결함은 닫혔고 계산은 테스트로 고정됐다. 그러나 **개인화 추천의 품질을 한 번도 재지 않았다** — 가중치 3/2/1과 게이트 3건은 판단값이다. 2026-09-07에 신호와 축을 하나씩 뺀 것도 신호의 성질을 따진 결과지 품질 측정이 아니다. 인덱스 재생성도 미실행이다. 이 단위는 "구조는 정리됐지만 효과는 미측정"이다.

**참신성.** 가중 평균과 L2 정규화는 평범하다. 다른 점은 (1) 결함 대부분이 **옆 모듈을 읽어야 보이는 것**이었고 그걸 전수 조사로 찾았다는 것, (2) 시간 축 삭제를 "느낌"이 아니라 정규화의 수학적 성질(전역 배수 소거)로 증명하고 그 증명을 테스트 이름으로 남긴 것, (3) 정책 판단을 등급 없이 사용자에게 넘긴 것, (4) **결국 세 축 중 둘과 신호 하나를 지웠다는 것** — 이 단위에서 한 일의 상당 부분이 더한 게 아니라 뺀 것이다.

## 한계와 풀 수 있는 방법

| 한계 | 풀 수 있는 방법 | 왜 아직 안 했나 |
|---|---|---|
| 품질 골든셋 없음 | 사용자 행동 시나리오 N개 + "이 추천이 맞는가" 채점. 레시피 골든셋과 같은 구조 | 채점 기준(무엇이 좋은 개인화인가)을 먼저 정해야 함 |
| 신규 사용자 프로필이 늦게 생김(검색 제거의 대가) | 상품 조회 이벤트를 받아 신호로 쓴다 | 발행 모듈 변경 필요 |
| 주문 취소 이벤트 발행부 없음 | `baro-order`에 `@TrackHistory(ORDER_CANCELLED)` | 발행 모듈 담당자 |
| ~~`quantity` 의미 차이~~ **해소** | — | 2026-09-07 수량 축을 통째로 빼면서 사라졌다. 곱하지 않으니 의미가 달라도 결과가 같다 |
| `X-User-Id` 위조로 로그 오염 | 게이트웨이 인증 필터 | 게이트웨이 담당자 |
| 게스트 행동 소실 | 로그인 병합 시 담기 이벤트 발행 | 발행 모듈 |
| 저장 직후 1초 refresh 지연 | 무시 가능(다음 갱신에서 따라잡음) | 강제 refresh는 쓰기 비용 |
| 인덱스 4개 재생성 미실행 | 사람이 직접 실행 | 되돌릴 수 없어 에이전트가 하지 않음 |

## 회고

- **경계를 넘는 기능은 경계 양쪽을 읽어야 한다.** 가장 큰 결함(가중치 전부 1)은 baro-ai 코드만 보면 완벽히 정상이었다.
- **"비동기"라고 적혀 있다고 비동기가 아니다.** 어노테이션이 있는 것과 프록시를 타는 것은 다르다.
- **정책과 결함을 구분해 넘겼다.** 시간 축이 무효라는 건 사실이지만, 뺄지 살릴지는 정책이라 등급을 매기지 않았다. 그 구분이 있어서 사용자 결정이 기록에 남았다.
- **효과를 재지 않은 채 구조만 정리한 단위다.** 이걸 숨기지 않는 게 이 문서의 역할이라고 생각한다.
- **면접에서 할 한 문장:** "장바구니 가중치가 발행 모듈과의 문자열 불일치로 전부 1이던 걸 옆 모듈 전수 조사로 찾았고, 취향 벡터를 상품 벡터 가중 평균으로 바꿔 임베딩 호출을 없앴습니다. 시간 감쇠는 정규화가 전역 배수를 소거한다는 성질로 무효임을 보이고 뺐습니다."
