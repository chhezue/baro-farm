# 001 — 캐싱 범위: 자동완성만, 나머지는 하지 않는다

> 상태: 확정 (2026-09-04)

baro-ai에서 캐시를 어디에 적용할지 정리한 결정이다. 기존에 있던 `CACHE_STRATEGY.md`(개인화·유사상품·레시피 추천까지 포괄한 제안 문서)를 대체한다.

## 맥락

`ProductIndexService.autocomplete()`에 `@Cacheable`이 붙어 있었지만 `@EnableCaching`이 어디에도 없어 실제로는 아무 효과가 없는 죽은 코드였다(`docs/specs/search/product-search-and-autocomplete.md` 리스크 항목으로 먼저 발견). 이 발견을 계기로 baro-ai 전체에서 캐싱이 실제로 필요한 지점이 어디인지 다시 정리했다.

## 결정

- **자동완성만 로컬 캐시(Caffeine)를 적용한다.** 최대 1,000개, TTL 5분 — `CacheConfig.java`.
- **개인화 추천·유사 상품 추천·레시피 추천 결과는 캐싱하지 않는다.**

## 근거

- 자동완성은 타이핑할 때마다 호출되고, 흔한 접두어("토마" 등)는 여러 사용자가 반복 요청한다 — 캐시 적중률이 높을 것으로 기대할 수 있는 유일한 지점이다.
- 개인화·유사상품 추천은 결과가 사용자·상품 단위로 갈라져(키 공간이 넓음) 같은 요청이 반복될 확률이 낮고, 최신성(방금 담은 장바구니가 바로 반영돼야 함)이 더 중요하다.
- 레시피 추천은 장바구니 조합에 따라 결과가 갈리는 데다 입력 자체가 자주 바뀌어 캐시 효율이 특히 낮다.
- 이 프로젝트는 실측 트래픽이 없다(서버 미배포 상태) — 위 판단은 "느릴 것 같다"는 추측이 아니라, 각 API의 **요청 키 공간과 반복률**이라는 구조적 사실에 근거했다.

## 고려한 대안

| 대안 | 기각 이유 |
|------|-----------|
| Redis로 전부 캐싱 | baro-ai만을 위해 새 공유 인프라를 추가하는 결정이라 5인 공용 저장소에서 혼자 정하기 부담스러움. 트래픽 실측 없이 도입할 근거도 약함 |
| Spring Boot 기본 캐시매니저(`ConcurrentMapCacheManager`)로 그냥 켜기 | TTL·최대 크기 제한이 전혀 없어(공식 문서: "프로덕션에 권장 안 함") 자동완성 키가 무제한으로 쌓임 |
| 개인화/추천 결과까지 캐싱 | 위 근거 참고 — 키 공간이 넓고 최신성이 중요해 효과 대비 리스크(stale 데이터)가 큼 |

## 트레이드오프

- Caffeine 캐시는 인스턴스별로 따로 존재한다 — baro-ai가 여러 인스턴스로 뜨면 인스턴스마다 캐시가 갈라져 적중률이 그만큼 낮아진다. 상품 데이터 자체는 ES에서 공유되므로 정합성 문제는 없다(최대 5분 지연 노출 정도).
- 추천 쪽에 트래픽이 실제로 몰리는 상황이 오면 이 결정은 재검토 대상이다 — 그때는 실측 데이터를 근거로 다시 결정한다.
