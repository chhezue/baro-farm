# 002 — 요리 재료명은 색인 시점에 1회 계산한다

> 상태: 확정 (2026-09-04) · 2026-09-04 amend — 정규식 폴백 제거

장바구니 기반 레시피 추천에서 "이 상품이 어떤 요리 재료인가"를 **언제** 계산할지 정한 결정이다.

## 맥락

레시피 추천 1회(`GET /api/v1/recommendations/recipes/{userId}`)가 OpenAI를 **3번 연달아** 호출하고 있었다. 앞의 두 번이 문제였다.

| # | 호출 | 하는 일 | 위치(변경 전) |
|---|------|---------|--------------|
| 1 | 상품명 배치 정규화 | `"곰곰 무항생제 신선한 대란, 30구, 1개"` → `"계란"` | `ProductNameNormalizer:130` |
| 2 | 보유 재료 추출 | 1번 결과를 다시 검증해 재료 목록 확정 | `RecipePromptService:103` |
| 3 | 레시피 후보 생성 | 보유 재료로 레시피 3개 생성 | `RecipePromptService:216` |

세 호출은 **직렬**이고, OpenAI 타임아웃 설정이 없어 요청 스레드를 무기한 붙잡을 수 있었다. 게다가 1번이 실패하면 `ProductNameNormalizer:157`의 폴백 루프가 상품 하나씩 개별 호출로 전환돼, 장바구니 N개에서 최악 **N+3회**가 됐다.

핵심은 **1·2번이 계산하는 값이 요청마다 달라지지 않는다**는 점이다. "대란 30구는 계란이다"는 상품의 성질이지 그 사용자의 장바구니 상태가 아니다. 같은 계란을 100명이 담으면 같은 계산을 100번 했다.

## 결정

- **`ProductDocument`에 `ingredientName`(`keyword`) 필드를 추가하고, 상품 색인 시점(Kafka `product-events` 소비)에 1회만 계산한다.**
- **레시피 추천 요청 경로에서는 그 필드를 읽기만 한다.** 상품 문서 조회 1회(`findAllById`)로 장바구니 전체를 처리한다.
- 요청 경로에 남는 LLM 호출은 **레시피 후보 생성 1회뿐**이다.

## 근거

- **현재 동작의 증거**: 하네스 `Explore` 서브에이전트가 호출 시퀀스를 파일·라인 단위로 추적해 "정상 3회 / 최악 N+3회, 전부 직렬, `@Async`·병렬 없음"을 확인했다. `OpenAiConfig`에 타임아웃 설정이 없다는 것도 grep으로 교차 확인했다(`ChatClient.builder(chatModel).build()`가 전부).
- **계산의 성질**: 1·2번의 입력은 상품명(+카테고리)뿐이고 사용자·시점에 의존하지 않는다. 즉 **요청 단위 계산이 아니라 상품 단위 속성**이다. 이건 "일반적으로 캐싱이 좋다"는 관습이 아니라, 입력 의존성에서 나오는 구조적 사실이다.
- **호출 빈도 비교**: 상품 색인은 상품 CRUD 이벤트에서만 발생하고 Kafka 컨슈머(요청 경로 밖)에서 처리된다. 추천 조회는 사용자가 장바구니를 볼 때마다 발생한다. 드물게 일어나는 쪽으로 비용을 옮긴 것이다.
- **2번 호출의 전제가 이 카탈로그에서는 성립하지 않는다.** 2번은 "장바구니에 주방용품·세제 같은 비식재료가 섞여 있을 수 있으니 걸러내자"는 의도였는데, `scripts/init-db/02-init-categories.sql`을 확인하면 **카테고리 22개가 전부 `AGRI_*`이고 루트가 `AGRI_DIRECT`(신선직송 농산물)**다. 비식재료 카테고리 자체가 없어 걸러낼 대상이 존재하지 않는다. "레시피에 쓸 만한가"라는 판단도 이미 `recipe-recommend.yml`의 `exclude-recipe-category-codes`가 결정적으로 처리하고 있었다 — 같은 판단을 LLM에 맡기지 않는 패턴이 코드베이스에 이미 있었다. (그 설정 자체는 목록이 계속 비어 있어 아무것도 걸러내지 못하는 죽은 분기였고 2026-09-09에 삭제했다. 이 결정의 근거였던 "패턴이 이미 있다"는 사실은 그때 사라졌지만, 결정 자체는 카테고리가 전부 `AGRI_*`이라는 앞 근거만으로도 성립한다.)
- **부수 효과**: 2번 호출이 사라지면서, LLM이 원본 상품명을 글자 그대로 되읊어야만 재료를 인정하던 대조 로직(`RecipeRecommendService:108`의 `originalProductNames.contains(...)`)도 함께 사라졌다. 모델이 공백 하나만 흘려도 그 재료가 조용히 없어지던 실패 경로였는데, 이제 재료명이 상품 문서에서 직접 오므로 대조할 필요 자체가 없다.

## 개선 후 검증 방법

프로덕션 APM이 없으므로(서버 미배포) 로컬에서 확인 가능한 방법만 쓴다.

1. **호출 횟수**: `spring.ai` 로깅이 DEBUG이므로, 추천 1회 요청 시 LLM 요청 로그가 **1건**만 찍히는지 확인한다(변경 전 3건).
2. **색인 경로**: 상품 이벤트 1건 소비 시 `ProductDocument.ingredientName`이 채워지는지 ES 문서를 직접 조회해 확인한다. 요리 재료가 아닌 상품(주방용품 등)은 빈 값이어야 정상이다.
3. **실패 시 빈 값**: 잘못된 Gemini 키로 기동해 상품 이벤트 1건을 발행한 뒤 ES 문서의 `ingredientName`이 빈 문자열이고 로그에 "재색인 대상" WARN이 남는지 확인한다.

## 고려한 대안

| 대안 | 기각 이유 |
|------|-----------|
| 요청 경로에 정규화 결과 캐시(Caffeine/Redis) 추가 | 캐시는 값이 **어딘가에 이미 있어야 할 때** 쓰는 우회책이다. 이 값은 상품의 속성이므로 상품 문서에 저장하는 게 정직하다. `001-autocomplete-caching.md`에서 추천 경로 캐싱을 하지 않기로 한 결정과도 충돌하지 않는다 |
| 두 LLM 호출을 하나로 합치기 | 호출이 3회에서 2회로 줄 뿐, 요청마다 상품 성질을 다시 계산하는 구조는 그대로다 |
| LLM 없이 정규식만 사용 | 정규식은 브랜드·단위 목록을 하드코딩해야 해서 새 상품 유형에 취약하다. 색인 시점이면 호출 빈도가 낮으므로 LLM 품질을 쓸 여유가 있다 |
| LLM 실패 시 정규식 폴백 (처음 채택했다가 2026-09-04 제거) | 폴백은 매핑이 아니라 브랜드·단위를 지우고 남은 글자를 돌려주는 것이라 `"대란 30구"` → `"대란"` 같은 그럴듯한 오답을 만든다. 상품명이 판매자 자유 입력(`ProductCreateRequest`는 `@NotBlank`뿐)이라 규칙으로는 안정적으로 못 뽑는다. 추천 코드는 이미 빈 값을 건너뛰고 재색인 대상으로 세므로, 실패는 빈 값으로 두는 편이 데이터가 더 정직하다. 실패 빈도는 Gemini 재시도(`docs/audits/cross-cutting/001-llm-call-infra.md` A-1)로 낮춘다 — 상세: `docs/audits/search/001-index-path.md` B-2·D-3 |
| 카테고리 코드만으로 재료명 결정 | 카테고리는 22개뿐이고 대부분 재료가 아니라 **분류**다. `AGRI_VEG_ROOT`(뿌리채소)로는 감자와 당근을 구분할 수 없다. 다만 `AGRI_LIVESTOCK_EGG`(계란)처럼 리프 카테고리가 곧 재료명인 경우도 있어, 카테고리를 **프롬프트 힌트로는 함께 넘긴다** |
| 장바구니 이벤트로 추천을 미리 계산해 저장 | 지금 구조에서 이미 요청당 LLM이 1회로 줄어 필요가 약해졌다. 남은 1회가 문제가 되면 그때 `CartEventConsumer`를 활용해 재검토한다 |

## 트레이드오프

무엇을 포기하고 얻었는지 분명히 해 둔다.

| 얻은 것 | 내준 것 |
|---------|---------|
| 추천 요청당 LLM 호출 3회에서 1회로 (최악 N+3회 경로 소멸) | **상품 CRUD 이벤트마다 LLM 호출이 1건 늘었다.** 요청 경로가 아니라 Kafka 컨슈머에서 처리되지만, 대량 적재 시에는 호출량이 상품 수에 비례한다 |
| 재료명이 상품 문서에서 직접 오므로 LLM이 상품명을 되읊는지 대조할 필요가 없어졌다 | **색인 처리 시간이 늘었다.** 임베딩에 이어 두 번째 원격 호출이 붙어, Kafka 리스너가 한 건을 처리하는 시간이 길어진다 |
| 같은 상품에 대해 매번 같은 재료명이 나온다 | **재색인 전까지 공백 구간이 있다.** 이 변경 이전 문서에는 `ingredientName`이 없어 그 상품은 보유 재료로 집계되지 않는다 |
| 상품이 바뀔 때만 계산하므로 중복 계산이 사라졌다 | **색인 시점 실패가 오래 남는다.** 요청 시점 계산은 다음 요청에 다시 시도되지만, 색인 시점 실패는 그 상품이 다시 색인될 때까지 빈 값으로 남는다. 빈 값을 다시 채우는 경로는 2026-09-09에 생겼다 — 관리자가 부르는 재색인 API(`POST /api/v1/search/admin/reindex`)가 상품을 원본에서 다시 읽어 색인한다. 다만 **빈 값만 고르는 것이 아니라 페이지 단위 전량 재색인**이다 |

## 영향

- **ES 매핑 변경** — `product` 인덱스에 `ingredientName` 추가. dev 모드라 전체 재색인으로 처리한다(`AGENTS.md` 운영 상태, `.claude/rules/baro-ai-performance-refactor.md` 데이터 마이그레이션 방침).
- **재색인 전까지는** `ingredientName`이 빈 문서가 보유 재료로 집계되지 않는다. `RecipeRecommendService`가 건너뛴 건수를 WARN 로그로 남긴다.
- API 응답 계약(`RecipeRecommendResponse`)은 **변경 없음**.
