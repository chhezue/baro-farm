# 기능·기술 문서 — 주제별 4편

baro-ai의 기능을 **주제 4개**로 나누고, 주제마다 "무엇을 왜 이렇게 만들었는가"를 한 편에 담은 문서 묶음이다. 값·계약은 스펙([`specs/`](../specs/README.md))이, 판단 근거는 결정 기록([`decisions/`](../decisions/README.md))과 감사([`audits/`](../audits/README.md))가 갖고 있으므로, 여기서는 그것들을 **한 기능의 이야기로 엮는다.** 처음 이 모듈을 보는 사람(면접관·신규 합류자·6개월 뒤의 나)이 스펙을 열기 전에 읽는 문서다.

## 언제 이 문서를 보는가

- baro-ai에 무슨 기능이 있고 각각이 어떻게 동작하는지 30분 안에 파악해야 할 때
- "왜 이렇게 만들었어요?"에 답해야 할 때 — 대안·근거·대가가 한 곳에 있다
- 포트폴리오 케이스 스터디([`portfolio/`](../portfolio/README.md))를 읽기 전에 기술 배경을 확인할 때

## 주제 4개

사용자가 부르는 이름으로 나눴다. 코드·스펙·감사 폴더의 **작업 단위**와 1:1로 대응한다 — 폴더명은 바꾸지 않고 문서 제목만 사용자 이름을 쓴다.

| 주제 (이 문서의 이름) | 작업 단위 (폴더) | 한 줄 | 문서 |
|---|---|---|---|
| **검색** | `keyword-search` | 상품 이벤트로 검색 인덱스를 채우고, 키워드 검색과 자동완성을 제공한다 | [`keyword-search.md`](keyword-search.md) |
| **임베딩 검색** | `vector-similarity` | 상품명을 벡터로 만들어 "비슷한 상품"을 찾고, 서로 겹치지 않게 고른다 | [`vector-similarity.md`](vector-similarity.md) |
| **장바구니 레시피** | `cart-recipe` | 장바구니 재료로 LLM이 레시피를 만들고, 부족한 재료를 살 수 있는 상품으로 연결한다 | [`cart-recipe.md`](cart-recipe.md) |
| **개인별 추천** | `taste-vector` | 장바구니·주문 행동을 취향 벡터로 바꿔 개인화 추천을 한다 | [`taste-vector.md`](taste-vector.md) |

경계에서 헷갈리기 쉬운 것 두 가지:

- **임베딩 검색과 개인별 추천은 뒷단을 공유한다.** 후보 조회(`VectorProductSearchService`)와 다양화(`MaxMinDiversityService`)는 "임베딩 검색" 문서가 설명하고, "개인별 추천" 문서는 기준 벡터(취향 벡터)를 어떻게 만드는지에 집중한다.
- **장바구니 레시피의 재료명은 검색 색인 시점에 만들어진다.** 상품이 색인될 때 LLM이 재료명을 뽑아 저장하고, 레시피 요청은 그 값을 읽기만 한다. 색인 경로는 "검색" 문서가, 재료명 추출의 이유는 "장바구니 레시피" 문서가 설명한다.

리뷰 분석(`review` 패키지)은 팀원 소유라 이 묶음에 없다([`REVIEW_ANALYSIS_PHASES.md`](../REVIEW_ANALYSIS_PHASES.md)). 챗봇은 미착수다([`specs/chat/chatbot.md`](../specs/chat/chatbot.md)).

## 이 문서 묶음의 형식 — 무엇을 참고해 어떻게 정했나

"기능/기술 문서"라는 이름의 정해진 표준은 없다. 세 가지를 비교해 이 저장소에 맞는 절 구성을 정했다.

| 참고 | 무엇을 가져왔나 | 무엇을 가져오지 않았나 |
|---|---|---|
| **Google 설계 문서**(Design Docs at Google) — 맥락·범위 / 목표·비목표 / 설계(시스템 맥락 다이어그램·API·저장) / 고려한 대안 / 교차 관심사 | "목표와 **하지 않는 것**"을 앞에 두는 것, "고려한 대안"을 트레이드오프와 함께 적는 것, 보안·관측·장애 같은 교차 관심사를 별도 절로 두는 것 | 구현 전에 쓰는 문서라 "제안" 어조다. 이 묶음은 구현·측정이 끝난 뒤 쓰는 문서라 "결정과 근거" 어조로 바꿨다 |
| **Diátaxis의 설명(explanation) 유형** — 왜 그런지·역사·대안·연결을 다루고, 절차와 참조 값은 넣지 않는다 | 절차(how-to)와 값(reference)을 여기 넣지 않고 링크로 보내는 원칙. 이 저장소의 템플릿 4종([`templates/`](../templates/README.md))이 이미 같은 틀이다 | 설명 유형만으로는 "실측 근거"와 "장애 시 동작"을 둘 자리가 없다 — 이 저장소는 근거 없는 변경을 금지하므로 그 자리를 추가했다 |
| **이 저장소의 기존 문서** — 스펙(참조), 결정 기록(설명), 감사(문제 해결), refactor-log(참조) | 값은 스펙에만, 결정은 ADR에만 두는 SSOT 원칙. 이 문서는 그것들을 **엮되 복제하지 않는다** | `FEATURES.md`처럼 API 예시와 기능 설명을 한 파일에 섞는 방식 — 값이 바뀔 때 두 곳을 고쳐야 해서 이미 drift가 났었다 |

그래서 정한 절 구성이다. 네 편 모두 같은 순서를 지킨다.

| 절 | 담는 것 | 출처 |
|---|---|---|
| 개요 | 무엇을, 누가, 어떤 흐름으로 — 3문장 | Diátaxis·저장소 템플릿 |
| 목표와 하지 않는 것 | 이 기능이 약속하는 것과 의도적으로 안 하는 것 | Google 설계 문서 |
| 한눈에 보는 흐름 | 시퀀스 다이어그램 1개 + 단계 표 | Google(시스템 맥락 다이어그램) |
| 어떻게 동작하는가 | 단계별 설명. 값은 스펙 링크 | Diátaxis·저장소 템플릿 |
| 핵심 설계 결정 | 결정마다 문제 → 대안 → 선택 → 근거 → 대가 | Google(대안)·ADR |
| 실측 근거 | 이 기능에서 실제로 잰 숫자와 원본 위치 | 이 저장소 고유 |
| 운영·장애 관점 | 실패하면 어떻게 되는지, 한도, 관측 | Google(교차 관심사) |
| 알려진 한계·다음 단계 | 지금 못 하는 것과 그 이유 | ADR 트레이드오프 |
| 관련 문서·코드 | 스펙·결정·감사·클래스 | 저장소 관례 |

**유형**은 설명(explanation)이고, 산출물 등록부에는 "기능·기술 문서"로 등록했다([`templates/README.md`](../templates/README.md)). 다이어그램은 mermaid 텍스트로 넣는다 — GitHub가 그대로 그려 준다.
