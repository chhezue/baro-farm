# 기능 및 기술 문서 (총 4편)

이 문서들은 `baro-ai`의 핵심 기능을 **4가지 주제**로 나누어 설명해요. 각각의 기능이 "무엇인지, 그리고 왜 이렇게 만들었는지"를 마치 옛날이야기를 들려주듯 편안하게 읽을 수 있도록 정리했어요.

구체적인 데이터 형식이나 API 규칙은 [스펙 문서](../specs/README.md)에, "왜 이런 기술을 썼을까?"에 대한 깊은 고민의 흔적은 [결정 기록](../decisions/README.md)과 [감사 문서](../audits/README.md)에 따로 모아두었어요. 

이 문서들은 복잡한 세부 사항을 열어보기 전에 꼭 읽어보는 **입문 가이드** 역할을 해요. 면접관님, 새로 합류하신 동료분, 그리고 6개월 뒤 기억이 가물가물해진 제 자신이 전체적인 큰 그림을 쉽게 잡을 수 있도록 쓰였어요.

## 언제 읽으면 좋을까요?

- `baro-ai`에 어떤 기능이 있고 어떻게 돌아가는지 30분 안에 빠르게 훑어보고 싶을 때
- "왜 하필 이런 방식으로 설계했나요?"라는 질문에 대한 대안, 선택의 이유, 그리고 아쉽지만 포기해야 했던 점(트레이드오프)을 한눈에 보고 싶을 때
- 포트폴리오를 작성하거나 면접을 준비하기 전, 기술적인 배경을 다시 한번 복습하고 싶을 때

## 4가지 핵심 주제

주제 이름은 우리가 평소에 부르는 친숙한 명칭으로 정했어요. 각 주제는 코드나 폴더의 이름과 1:1로 똑같이 맞아떨어져요. 폴더명은 영문을 유지하되, 문서 제목만 알기 쉽게 바꿨어요.

| 주제 (이 문서의 이름) | 작업 단위 (폴더명) | 한 줄 요약 | 자세히 보기 |
|---|---|---|---|
| **검색** | `keyword-search` | 상품 데이터를 모아두고(색인), 키워드로 검색하거나 자동완성하는 기능을 제공해요. | [`keyword-search.md`](keyword-search.md) |
| **임베딩 검색** | `vector-similarity` | 상품의 이름을 숫자들의 배열(벡터)로 바꿔서 "비슷한 상품"을 찾고, 너무 뻔한 결과만 나오지 않게 골고루 섞어줘요. | [`vector-similarity.md`](vector-similarity.md) |
| **장바구니 레시피** | `cart-recipe` | 장바구니에 담긴 재료를 보고 AI(LLM)가 딱 맞는 레시피를 제안해 줘요. 부족한 재료는 바로 살 수 있게 도와주고요. | [`cart-recipe.md`](cart-recipe.md) |
| **개인별 추천** | `taste-vector` | 장바구니에 담거나 주문했던 내역을 바탕으로 사용자의 '취향'을 분석해, 그 사람에게 꼭 맞는 상품을 추천해요. | [`taste-vector.md`](taste-vector.md) |

### 💡 헷갈리기 쉬운 두 가지 포인트

- **'임베딩 검색'과 '개인별 추천'은 사실 속에서 같은 원리로 돌아가요.** 
  비슷한 상품 후보를 찾고 골라내는 과정은 "임베딩 검색" 문서에서 주로 설명해요. 반면, "개인별 추천" 문서는 사용자의 취향을 어떻게 분석해서 기준을 세우는지에 초점을 맞춥니다.
- **'장바구니 레시피'의 재료명은 미리 뽑아둬요.** 
  상품 데이터를 저장할 때, AI가 미리 재료 이름만 쏙쏙 뽑아서 저장해 둬요. 나중에 사용자가 레시피를 물어보면 미리 만들어둔 값을 빠르게 꺼내 주기만 하면 되죠. 이 과정은 "검색" 문서와 "장바구니 레시피" 문서에 나뉘어 설명되어 있어요.

> 참고로 리뷰 분석 기능(`review` 패키지)은 다른 팀원이 담당하고 있어서 이 묶음에는 빠져 있어요([관련 내용 보기](../REVIEW_ANALYSIS_PHASES.md)). 챗봇 기능은 아직 개발을 시작하지 않았어요([스펙 문서 보기](../specs/chat/chatbot.md)).

## 이 문서들은 어떻게 구성되어 있나요?

"기능 명세서"나 "기술 문서"라고 하면 딱딱하고 지루할 것 같지만, 저희는 3가지 훌륭한 문서를 참고해서 우리에게 가장 잘 맞는 형태를 만들었어요.

| 참고한 레퍼런스 | 적용한 점 | 적용하지 않은 점 |
|---|---|---|
| **Google 설계 문서**(Design Docs at Google) | "목표와 **하지 않는 것(비목표)**"을 명확히 밝혔어요. 여러 대안들의 장단점을 비교하고, 장애나 보안 같은 공통 관심사도 다루었어요. | 구글의 문서는 개발 전에 쓰는 "제안서" 느낌이지만, 우리 문서는 이미 개발이 끝난 뒤에 쓰기 때문에 "어떻게 결정했는지" 설명하는 데 집중했어요. |
| **Diátaxis의 설명(explanation) 유형** | 너무 길고 복잡한 내용이나 숫자들은 문서에 억지로 끼워 넣지 않고, 링크를 걸어 따로 볼 수 있게 뺐어요. | 단순한 설명만으로는 부족해서, "실제로 측정한 데이터"와 "장애가 났을 때 어떻게 동작하는지"를 적는 칸을 새로 만들었어요. |
| **우리 팀의 기존 문서들** | 같은 내용을 여기저기 중복해서 쓰지 않도록 했어요. 데이터 형식은 스펙 문서에, 결정 사항은 ADR 문서에만 두고 이 문서가 징검다리 역할을 해요. | API 예시나 상세한 코드 이야기를 섞어 쓰지 않고, 철저하게 역할을 나눴어요. |

이러한 고민을 거쳐 만들어진 문서의 목차는 다음과 같아요. 4편 모두 이 순서를 따라요.

| 목차 | 담겨있는 내용 |
|---|---|
| **개요** | 무엇을, 누가, 어떤 흐름으로 처리하는지 3문장으로 짧게 요약해요. |
| **목표와 하지 않는 것** | 이 기능이 꼭 해내야 하는 것과, 굳이 하지 않기로 쳐낸 부분을 밝힙니다. |
| **한눈에 보는 흐름** | 이해를 돕는 그림 1개와 단계별 표를 제공해요. |
| **어떻게 동작하는가** | 기능이 돌아가는 순서를 설명해요. |
| **핵심 설계 결정** | 어떤 문제에 부딪혔고 → 어떤 대안이 있었으며 → 무엇을 선택했고 → 왜 그랬는지(무엇을 포기했는지) 설명해요. |
| **실측 근거** | 이 기능을 만들면서 실제로 측정한 속도나 성능 데이터를 밝힙니다. |
| **운영·장애 관점** | 만약 실패하면 어떻게 되는지, 시스템이 어디까지 버틸 수 있는지 다룹니다. |
| **알려진 한계·다음 단계** | 지금은 안 되는 것들과 그 이유를 솔직하게 적어요. |
| **관련 문서·코드** | 연관된 스펙, 결정 문서, 핵심 코드의 위치를 안내해요. |

* 문서에 나오는 그림들은 별도의 프로그램 없이 GitHub에서 바로 보여주는 문법(mermaid)을 사용해 그렸어요.
