# Plain-Language Reporting (비전공자용 쉬운 설명)

**적용 범위:** 사용자에게 **말로 설명하는 모든 곳** — 채팅 응답, `{{감사 로그}}/refactor-log.md`, 감사 요약, PR 설명, 완료 보고.
**적용 안 함:** `.java` 파일의 `//`·Javadoc 주석. 그건 `java-comments.md`(독자=신규 서버 개발자, WHAT 설명 금지)가 SSOT — 이 규칙과 충돌하지 않는다(2026-08-04 사용자 결정: 코드는 개발자 컨벤션 유지, 설명은 보고서·채팅에서만 쉽게).

## 원칙

기술 변경을 사용자에게 보고할 때, 아래를 지킨다:

1. **용어를 풀어쓰거나 처음 나올 때 짧게 설명** — "트랜잭션", "커넥션 풀", "캐싱", "AOP" 같은 말을 설명 없이 쓰지 않는다. 예: "DB 커넥션 풀"이 아니라 "DB에 접속하는 자리(개수 제한 있음)".
2. **비유·결과 중심으로 왜 문제였는지 설명** — 메커니즘(코드가 어떻게 동작하는지)보다 **결과**(무엇이 느려지거나 위험했는지, 사용자·서비스에 어떤 영향인지)를 먼저 말한다.
3. **분량은 늘어나도 됨** — 개발자용 주석은 짧아야 하지만, 사용자 보고는 이해가 우선이라 문장이 길어지는 걸 감수한다.
4. **과장·공포 조장 금지** — "심각한 버그"처럼 부풀리지 않는다. 실제 영향 범위(예: "지금 당장 문제는 아니었지만, 트래픽이 늘면 문제가 될 수 있었다")를 정확히 전달한다.

## 예시 (2026-08-04, auth 리팩토링 A-1 사례)

- **개발자용 코드 주석** (유지): `// 소셜 토큰을 검증하고... DB 쓰기 트랜잭션 밖에서 먼저 끝내, provider 장애·지연이 DB 커넥션 풀을 붙잡지 않게 함`
- **사용자 보고용 설명**: "카카오/구글/애플 서버에 로그인 확인을 받는 동안(느려질 수 있음) 우리 DB 접속 자리를 계속 붙잡고 있었어요. 카카오가 느려지면 로그인과 상관없는 다른 기능까지 다 같이 느려질 위험이 있었는데, 이제 확인부터 먼저 받고 DB 저장은 그다음에 짧게 하도록 순서를 바꿔서 그 위험을 줄였어요."

## 언제 적용

- 완료 보고, 변경 요약, 감사 결과 설명 등 **사용자가 직접 읽는 모든 응답**
- `safe-refactor`·`specify` 등 스킬의 "사용자에게 요약 보고" 단계
- 순수 내부 진행 상황 로그(TaskUpdate 등)는 대상 아님
