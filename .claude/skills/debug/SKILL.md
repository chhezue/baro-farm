# Bug 재현 · 원인 분리 · 수정

전용 스킬이 없던 자리를 대신한다 — `core-tools.md` "도구 우선순위" 판단 근거 참고. 추측으로 고치지 않고 아래 순서를 따른다.

**이 스킬은 `core-workflow.md` 사이클의 C 트랙이다.** 재현·원인 분리가 **G1 리서치**(원인이 외부 라이브러리 동작이면 `researcher`로 공식 문서 확인 — 버전 차이가 원인인 경우가 많다), 수정 범위 합의가 **G2 승인**, 회귀 확인이 **G3 검증**에 대응한다.

## When to Use

- 버그 리포트를 받았거나 `{{테스트 명령}}`가 실패했을 때
- "안 되는데요" 같은 증상 보고를 받았을 때 — 원인이 로컬 코드 검토만으로 안 잡힐 수 있음

## Steps (로컬 재현 가능한 경우)

1. 실패를 `{{테스트 명령}}` 또는 재현 스텝으로 고정 — 추측으로 고치지 않는다
2. 로그·스택트레이스에서 원인을 좁힌다 (필요 시 `Explore` 서브에이전트로 관련 코드 탐색)
3. 최소 수정 → 같은 테스트로 재현 확인 → 회귀 확인을 위해 전체 `{{테스트 명령}}`

## 프로덕션에서만 재현되는 버그

로컬 코드 검토로 원인이 안 잡히는 경우, 또는 클라이언트가 보는 증상이 실제 서버 동작과 다를 수 있는 경우. 추측으로 결론 내리지 말고 실제 EC2 로그·DB를 먼저 본다.

- SSH 접속 정보를 에이전트 메모리(reference 타입)에서 먼저 확인 — 있으면 사용자에게 다시 묻지 않고 바로 접속해 `docker logs`/DB 조회로 원인을 좁힌다. 없으면 사용자에게 요청
- **EC2 A(App+Nginx)·B(MySQL)·C(Monitoring: Loki+Grafana) 전부 직접 접근 가능** — 셋 중 필요한 인스턴스에 바로 SSH해 조사한다. 실제 IP·키 경로는 에이전트 메모리(`ec2-ssh-access`)에서 확인
- **AWS CLI는 항상 프로젝트 전용 `--profile`로 실행** — 생략하면 무관한 기본 계정으로 빠진다. 상세: 에이전트 메모리(`aws-cli-profile`)
- **읽기(로그 조회·DB SELECT)는 바로 진행**하되, 원인이 애플리케이션 코드면 이 레포에서 고쳐 정상 워크플로(PR·CI/CD)로 배포 — 운영 서버에 직접 手patch·설정 변경은 하지 않음
- 이 정책 자체는 커밋되지만 실제 IP·키 경로 등 민감한 접속 정보는 여기 적지 않는다 — 에이전트 메모리에만 보관

## TDD 메모

전용 스킬은 없다. 핵심 로직·스펙 Must만 선행 테스트를 권장하고, 단순 DTO/와이어링은 "유의미한 테스트만" 원칙(`testing.md`)을 따른다.

## 금지

- 재현 없이 추측으로 코드 수정
- 프로덕션 버그를 로컬 코드 리뷰만으로 단정
- 운영 서버에 직접 手patch·설정 변경
